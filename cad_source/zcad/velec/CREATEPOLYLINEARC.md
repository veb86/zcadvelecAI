## 1. Краткие исходные данные из POLYLINEARC.md

Документ-предшественник установил следующее (детали — в [`POLYLINEARC.md`](POLYLINEARC.md)):

* Дуговой сегмент полилинии хранится одним числом **Bulge** (групповой код `42`) у вершины, с
  которой начинается сегмент: `bulge = tan(θ/4)`, где `θ` — центральный угол дуги.
* Преобразование `Bulge ↔ (центр, радиус, углы)` — простая и надёжная математика, **наименее
  рискованная часть** задачи.
* **Основная сложность — не Bulge, а корректная отрисовка дуги совместно с Width и Linetype** и
  особенно **стыковка соседних сегментов**.
* Постоянная ширина на дуге строится точно (концентрические дуги — «кольцевой сектор»); переменная
  ширина и стыки требуют тесселяции и аккуратной геометрии (miter по касательной, защита от
  выворота внутренней границы при `R − w/2 ≤ 0`).
* Linetype на дуге должен раскладываться по **длине дуги** (`R·θ`), а не по длине хорды; требуется
  непрерывность фазы между сегментами и поддержка режима **PLINEGEN** (бит 128 кода 70).
* Инфраструктура частично готова: есть класс дуги `GDBObjArc`, есть quad-отрисовка ширины для
  прямых, а bulge уже доходит до DWG-структуры `TDWGLWPolylineVertex.Bulge`, но **отбрасывается**
  при конвертации в `GDBObjLWPolyline`.

Настоящий документ переходит от «что сложно» к «как именно это внедрять в текущий код».

## 2. Фактическое состояние кода: что есть в пайплайне построения полилинии

Все ссылки проверены по исходникам ветки. Центральный модуль —
`cad_source/zengine/core/entities/uzeentlwpolyline.pas`.

### 2.1. Структуры данных полилинии

```pascal
GLLWWidth=record           // ширина одного сегмента (uzeentlwpolyline.pas:36)
  startw:double;           // начальная ширина
  endw:double;             // конечная ширина
  hw:boolean;              // "has width" — сегмент утолщённый
  quad:GDBQuad2d;          // четырёхугольник полосы (4 точки) — ТОЛЬКО для прямой
end;

GDBObjLWPolyline=object(GDBObjWithLocalCS)        // :50
  Closed:boolean;
  Vertex2D_in_OCS_Array:GDBpolyline2DArray;       // вершины (x,y) в OCS
  Vertex3D_in_WCS_Array:GDBPoint3dArray;          // вершины в WCS (для отрисовки/снапа)
  Width2D_in_OCS_Array:GDBLineWidthArray;         // массив GLLWWidth (по сегментам)
  Width3D_in_WCS_Array:TWidth3D_in_WCS_Vector;    // quad в WCS (по сегментам)
  Square:double;
  ...
```

Ключевой факт: **вершина — это `TzePoint2d` (только x, y)**, тип `GDBpolyline2DArray`
(`UGDBPolyLine2DArray.pas`). Поля Bulge нет нигде в цепочке хранения полилинии. Ширина хранится
**параллельным массивом** `Width2D_in_OCS_Array` — это и есть готовый образец, «куда» добавлять
параллельный массив bulge.

### 2.2. Конвейер построения (`FormatEntity`)

`FormatEntity` (`:651`) последовательно вызывает:

1. `createpoint` (`:668`) — переносит 2D-вершины из OCS в WCS (`Vertex3D_in_WCS_Array`)
   простым умножением на `objMatrix`. **Здесь нет никакой тесселяции** — каждая вершина даёт ровно
   одну точку WCS.
2. `CalcWidthSegment` (`:690`) — для каждого сегмента считает нормаль к **хорде** `P1→P2`, строит
   четырёхугольник `quad[0..3]` (опорный случай «утолщённая прямая», POLYLINEARC.md §4.2) и затем
   во втором проходе делает **miter-стыковку** соседних quad через `intercept3dmy2` (пересечение
   границ полос, `:774`).
3. `CalcSquare` (`:628`) — площадь по формуле шнурков, **по вершинам-хорде**.
4. `calcbb` — bounding box по вершинам.

### 2.3. Отрисовка (`DrawGeometry`, `:440`)

* На низком LOD (`simplydraw`) — рисует упрощённо отдельными линиями (`:455`).
* На нормальном LOD — двумя проходами: сначала заливка `DrawQuad3DInModelSpace` для сегментов с
  `hw=True` (`:487`), затем осевые/контурные линии `DrawLine3DInModelSpace` (`:497`).
* **Важная архитектурная деталь:** `GDBObjLWpolyline.DrawGeometry` рисует **напрямую через
  `dc.drawer`** и **не использует** `Representation.DrawPolyLineWithLT`. Тип линии (Linetype) к
  полосе ширины тут фактически не применяется через стандартный LT-механизм. Для сравнения, дуга
  (`uzeentarc.pas:433`), сплайн (`uzeentspline.pas:226`), окружность (`uzeentcircle.pas:275`) и
  «тяжёлая» полилиния (`uzeentpolyline.pas:139`) рисуются именно через
  `Representation.DrawPolyLineWithLT` (определена в `uzeenrepresentation.pas:229` →
  `uzglgeometry.pas:681`), который раскладывает штрихи типа линии по длине ломаной с помощью
  сегментатора `ZSegmentator`.

  Это означает: добавление дуг с поддержкой Linetype почти неизбежно потребует **либо** перевести
  отрисовку осевой линии LWPolyline на `DrawPolyLineWithLT`, **либо** продублировать раскладку
  штрихов в собственном коде LWPolyline. Это самостоятельный архитектурный выбор, не зависящий
  напрямую от способа хранения дуги.

### 2.4. Ввод/вывод

* **DXF чтение** `LoadFromDXF` (`:510`): обрабатываются коды `8,62,90,10,20,38,40,41,43,70,210/220/230,370`.
  **Кода `42` в `case` нет** — bulge при чтении DXF молча отбрасывается (`else rdr.SkipString`).
* **DXF запись** `SaveToDXF` (`:584`): выводит `90,70,38,10,40,41`. **Код `42` не выводится.**
* **DWG импорт** `uzedwgentlwpolyline.pas:57-67`: копирует `Props.Vertices[i].X/Y/StartWidth/EndWidth`,
  но **не копирует** `Props.Vertices[i].Bulge`, хотя поле уже прочитано на уровне
  `dwgproc.pp` (`TDWGLWPolylineVertex.Bulge`).
* **Proxy-парсер** `uzeentproxyparserlwpolyline.pas`: bulge читается из бит-потока, но прямой
  комментарий (`:262`) гласит, что он игнорируется, а подпримитивы строятся прямыми
  (`BuildLinesFromVertices`).

### 2.5. Вывод по состоянию кода

«Скелет» данных и построения целиком ориентирован на **прямые сегменты**: вершина без кривизны,
ширина = четырёхугольник по хорде, miter = пересечение четырёхугольников, площадь = по вершинам.
Любой вариант поддержки дуг обязан определить, **в какой момент конвейера** дуга превращается в то,
что эти алгоритмы умеют обрабатывать (прямые/quad), либо **насколько глубоко** в конвейер
протягивается «настоящая» дуга.

## 3. Ключевые точки интеграции (общие для всех вариантов)

Независимо от выбранного варианта, минимальный набор затрагиваемых мест одинаков. Различается
лишь объём изменений в геометрии/отрисовке.

| № | Действие | Файл / метод | Затрагивается во вариантах |
|---|---|---|---|
| 1 | Хранение bulge на вершину | `uzeentlwpolyline.pas` — новый параллельный массив рядом с `Width2D_in_OCS_Array` | A, B, C |
| 2 | Чтение кода 42 | `LoadFromDXF` (`:531` `case byt`) — ветка `42:` | A, B, C |
| 3 | Запись кода 42 | `SaveToDXF` (`:603` цикл по вершинам) | A, B, C |
| 4 | Перенос bulge из DWG | `uzedwgentlwpolyline.pas:57-67` — копировать `Props.Vertices[i].Bulge` | A, B, C |
| 5 | Bulge в proxy-объектах | `uzeentproxyparserlwpolyline.pas` — тесселяция вместо игнорирования | A, B, C (опционально) |
| 6 | Геометрия bulge→дуга | новый служебный модуль формул (центр, R, углы, длина, точка, касательная) | B, C (A — частично) |
| 7 | Осевая линия (createpoint) | `createpoint` (`:668`) | A (расширяется), C (расширяется) |
| 8 | Геометрия ширины | `CalcWidthSegment` (`:690`) | A (через п.7), B (ветвление), C (через тесселяцию) |
| 9 | Отрисовка | `DrawGeometry` (`:440`) | B (ветвление), A/C (через расширенные массивы) |
| 10 | Площадь / BBox | `CalcSquare` (`:628`), `getoutbound` (`:277`) | B, C (точно), A (приближённо) |
| 11 | Снап/контрольные точки | `startsnap`/`getsnap` (`:173`,`:190`), `AddControlpoints` (`:366`) | B, C (центр/середина дуги), A (теряет) |
| 12 | Linetype вдоль осевой | связать `DrawGeometry` с `DrawPolyLineWithLT` либо собственная раскладка | A, B, C (ортогональный выбор) |

Пункты 1–5 — «механическая» часть (низкий риск, см. POLYLINEARC.md §9.3) и **являются общим
фундаментом**: их разумно выполнить отдельной первой фазой («round-trip без потерь») в любом
варианте.

## 4. Переиспользуемые алгоритмы, уже имеющиеся в ZCAD

Эти находки прямо влияют на оценку трудоёмкости — часть работы уже сделана в смежных подсистемах.

### 4.1. Готовая тесселяция Bulge → ломаная (HATCH-границы)

В `cad_source/zengine/core/entities/uzeboundarypath.pas` уже есть рекурсивная тесселяция дуги по
bulge — она применяется при загрузке контуров штриховки:

```pascal
procedure DrawArc(constref p1,p2:TzePoint2d;const bulge:double;
                  var currpath:GDBPolyline2DArray;divcount:integer);   // :166
var l,h,nextbulge:double; ...
begin
  ...
  h:=l*bulge/2;                              // сагитта = |bulge|·L/2 (POLYLINEARC.md §3.2)
  pac:=pc-n*h;                               // точка на дуге (середина)
  if divcount=-1 then
    divcount:=min(max(2,abs(round(bulge*2))),5);   // 2..5 подразбиений
  ...
  nextbulge:=bulge/(1+sqrt(1+bulge*bulge));  // bulge половинной дуги
  DrawArc(p1,pac,nextbulge,currpath,divcount);
  DrawArc(pac,p2,nextbulge,currpath,divcount);
end;
```

`loadPolyWithBulges` (`:206`) читает код `42` из DXF и наполняет `GDBPolyline2DArray` точками. Это
**прямой прототип** для варианта A и для тесселяционной части варианта C.

**Ограничение, которое нужно учесть:** число подразбиений здесь фиксировано (2..5 по величине
bulge) и **не зависит от зума/LOD**. Для границ штриховки это приемлемо, но для видимой полилинии
на больших зумах дуга будет выглядеть гранёной. Адаптивную тесселяцию по экранному допуску
(POLYLINEARC.md §8.9, формула `N = ceil(θ/(2·arccos(1−tol/R)))`) придётся добавить отдельно —
ориентир уже есть в `GDBObjArc.createpoints` (см. 4.2).

### 4.2. Готовая адаптивная тесселяция дуги по LOD (`GDBObjArc`)

`uzeentarc.pas:createpoints` (`:527`) вычисляет число сегментов по зуму:

```pascal
l:=r*angle/(dc.DrawingContext.zoom*10);
if (l>maxlod)or dc.MaxDetail then lod:=maxlod      // maxlod = 60..100
else begin lod:=round(l); if lod<5 then lod:=5; end;
Vertex3D_in_WCS_Array.SetSize(lod+1);
... SinCos(startangle+i/lod*angle, ...)            // точки дуги
```

Эта формула — готовый источник адаптивного `N` для любого варианта, где дуга превращается в
осевую ломаную.

### 4.3. Полноценная сущность дуги `GDBObjArc`

`GDBObjArc` (`uzeentarc.pas`) умеет всё, что нужно для дуги-примитива: хранение (центр, R,
start/end угол), корректный BBox с учётом квадрантов (`getoutbound` `:439`), снапы (центр,
середина, концы — `getsnap` `:664`), восстановление параметров дуги из 3 точек
(`GetArcParamFrom3Point2D`, используется в `rtmodifyonepoint` `:766`). Это эталон для варианта B
(EXPLODE дуги → `GDBObjArc`, POLYLINEARC.md §6.3) и поставщик готовых формул для варианта C.

### 4.4. LT-совместимая отрисовка ломаной `DrawPolyLineWithLT`

`uzglgeometry.pas:681` раскладывает штрихи типа линии вдоль произвольной ломаной (через
`ZSegmentator`, учёт замкнутости и `ltgen`). Если осевую линию дугового участка представить
ломаной (тесселяция), раскладка Linetype по **длине ломаной** автоматически приблизит раскладку по
**длине дуги** (тем точнее, чем мельче тесселяция) — это снимает значительную часть сложности
Linetype для вариантов A и C, не реализуя раскладку «по дуге аналитически».

### 4.5. Низкоуровневое чтение bulge уже работает

`dwgproc.pp` (`TDWGLWPolylineVertex.Bulge`, чтение `num_bulges`) и proxy-парсер уже **извлекают**
bulge из бинарных форматов. То есть «вход» данных частично готов — нужно лишь не терять значение
при конвертации в `GDBObjLWPolyline`.

## 5. Вариант A — тесселяция дуги в линейные сегменты на этапе построения

### 5.1. Основная идея

Bulge хранится у вершины (общий фундамент, раздел 3), но на этапе `FormatEntity`/`createpoint`
каждый **дуговой** сегмент **разворачивается в набор коротких прямых подсегментов**. Дальше по
конвейеру (ширина, miter, заливка, отрисовка, снап) полилиния — это обычная ломаная из прямых, и
существующий код работает без изменений.

По сути это перенос уже работающего в `uzeboundarypath.pas` подхода (раздел 4.1) в конвейер
LWPolyline, с заменой фиксированного `divcount` на адаптивный `N` из `GDBObjArc.createpoints`
(раздел 4.2).

### 5.2. Принцип работы

1. После чтения bulge формируется «исходная» (редактируемая) геометрия: вершины + bulge.
2. В `createpoint` (или новой фазе перед `CalcWidthSegment`) строится «развёрнутая» геометрия:
   для дугового сегмента вставляются промежуточные вершины с **интерполированной шириной**
   (`startw→endw` линейно по подсегментам).
3. `CalcWidthSegment`, miter, `DrawGeometry`, `CalcSquare`, BBox работают над развёрнутой
   геометрией как над обычной ломаной.
4. Для записи DXF/DWG и редактирования используется **исходная** (неразвёрнутая) геометрия с
   bulge — иначе round-trip потеряет дугу и «размножит» вершины.

Ключевое требование — **держать две геометрии раздельно**: исходную (vertex+bulge, для I/O и
редактирования) и производную (тесселированную, для построения/отрисовки). Сейчас в классе есть
ровно такое разделение по другому поводу: `Vertex2D_in_OCS_Array` (исходная) →
`Vertex3D_in_WCS_Array` (производная). Вариант A естественно встраивается в это разделение.

### 5.3. Влияние на критичные механизмы

* **Постоянная ширина:** работает «бесплатно» — каждый подсегмент получает quad через
  существующий `CalcWidthSegment`. Геометрически это аппроксимация кольцевого сектора
  многоугольником (гранёность видна только на грубой тесселяции).
* **Переменная ширина:** работает естественно — интерполяция `startw→endw` по подсегментам даёт
  то самое разбиение на трапеции, которое POLYLINEARC.md §4.4 называет практическим подходом всех
  CAD. Это **сильная сторона** варианта.
* **Контуры толстых полилиний / заливка:** существующий двухпроходный `DrawGeometry`
  (quad-заливка + контур) применяется без изменений.
* **Стыки сегментов:** miter работает, но между **множеством** мелких подсегментов. На стыке
  дуга↔прямая miter получится «по касательной» автоматически, потому что последний подсегмент дуги
  уже почти касателен (POLYLINEARC.md §4.5). Риск «заломов» снижается с ростом `N`.
* **Типы линий:** если осевую линию рисовать через `DrawPolyLineWithLT` по тесселированной ломаной,
  штрихи раскладываются по длине ломаной ≈ длине дуги (раздел 4.4). Непрерывность фазы между
  сегментами выходит автоматически (вся полилиния — одна ломаная). PLINEGEN частично
  моделируется выбором замкнутости/режима ломаной.

### 5.4. Преимущества

* Минимальные изменения в самой сложной части — геометрии ширины и стыков: они **не трогаются**.
* Переиспользует уже отлаженный код тесселяции bulge (раздел 4.1) и LOD (раздел 4.2).
* Переменная ширина и стыки «дуга↔дуга» получаются без отдельной тяжёлой математики
  (POLYLINEARC.md §4.7 относит их к высокой сложности — здесь они сводятся к набору прямых).
* Самый быстрый путь к визуально работающему результату.
* Низкий и понятный риск.

### 5.5. Недостатки и риски

* **Раздутие числа вершин** производной геометрии; при больших полилиниях с дугами растёт память и
  время `CalcWidthSegment`/miter (O(N) по подсегментам).
* **Потеря точных дуговых сущностей в производной геометрии:** снап к центру/квадрантам дуги, точная
  середина дуги, точный BBox и точная площадь сектора — **отсутствуют** или приближены. Это прямо
  отмечено как риск в POLYLINEARC.md §8.5–8.7. Снап к концам и «ближайшая точка» работают (вершины
  на дуге есть).
* **Грубость при зуме**, если тесселяция не пересчитывается при изменении масштаба (нужно завязать
  `N` на LOD и пересчитывать в `FormatEntity`, как у `GDBObjArc`).
* **EXPLODE** даст набор `LINE` вместо `ARC` (отличие от поведения AutoCAD, POLYLINEARC.md §6.3) —
  если только не реализовать explode по исходному bulge отдельно.
* Необходимость аккуратно не дать тесселированным вершинам «протечь» в `SaveToDXF` (round-trip).

### 5.6. Влияние на производительность

Линейно по числу подсегментов. Для тонких/коротких дуг на типичных чертежах накладные расходы
малы; основной риск — чертежи с тысячами широких дуг на высоком LOD. Смягчается адаптивным `N` и
путём `simplydraw` (низкий LOD уже реализован в `DrawGeometry`).

### 5.7. Поэтапный план

* **Этап A0 — фундамент данных (round-trip).**
  Цель: не терять bulge. Сделать: параллельный массив bulge; чтение/запись кода 42; перенос из DWG;
  тесселяция в proxy. Результат: дуги сохраняются без потерь (даже если рисуются хордой). Критерий:
  загрузка→сохранение `polylinearc.dxf` сохраняет код 42 и значения вершин.
* **Этап A1 — тесселяция осевой линии.**
  Цель: видимые дуги. Сделать: в `createpoint` разворачивать дуговые сегменты в подсегменты
  (адаптивный `N`). Результат: дуга видна как гладкая кривая, BBox/снап концов корректны. Критерий:
  визуальное совпадение формы дуги с `GDBObjArc` той же кривизны.
* **Этап A2 — ширина по тесселяции.**
  Цель: толстые дуги. Сделать: интерполяция ширины по подсегментам, прогон через `CalcWidthSegment`.
  Результат: постоянная и переменная ширина на дуге рисуются и заливаются. Критерий: отсутствие
  разрывов полосы на стыках дуга↔прямая при `N` от LOD.
* **Этап A3 — типы линий.**
  Цель: Linetype на дугах. Сделать: перевести осевую отрисовку на `DrawPolyLineWithLT` (или
  раскладку по тесселированной длине). Результат: DASHED/HIDDEN/CENTER ложатся по длине дуги.
  Критерий: визуальная непрерывность штрихов через дугу.

## 6. Вариант B — дуга как самостоятельный тип сегмента

### 6.1. Основная идея

Bulge хранится у вершины, и дуга **остаётся дугой на всю глубину конвейера**. Алгоритмы построения
геометрии и отрисовки получают **ветвление «прямая/дуга»**: для дуги строятся аналитические
концентрические дуги (постоянная ширина), считаются точные центр/радиус/углы, длина дуги, точная
площадь сектора, точный BBox, корректные снапы. Производная геометрия (тесселяция) используется
только как финальный примитив отрисовки, но все измерения и стыки делаются по «настоящей» дуге.

### 6.2. Принцип работы

1. Новый служебный модуль формул `bulge → (центр, R, α0, α1, длина, точка, касательная)` (по
   эталону `ezdxf.math._bulge`, POLYLINEARC.md §7.2; формулы уже частично есть в `GDBObjArc`).
2. `CalcWidthSegment` ветвится:
   * прямая → существующий quad;
   * дуга, постоянная ширина → **кольцевой сектор** (внешняя/внутренняя концентрические дуги,
     радиусы `R±w/2`, POLYLINEARC.md §4.3, §8.8) с защитой от выворота при `R−w/2≤0`;
   * дуга, переменная ширина → тесселяция в трапеции (как в варианте A, но локально).
3. Стыки считаются по **касательной к дуге** (miter/bevel/round), включая пересечение двух
   смещённых дуг (POLYLINEARC.md §4.5).
4. `DrawGeometry` ветвится: для дуги вызывает дуговую заливку/контур; осевая дуга рисуется
   тесселированной ломаной через `DrawPolyLineWithLT` с раскладкой штрихов по **длине дуги**.
5. `CalcSquare`, `getoutbound`, снапы, EXPLODE — расширяются дуговыми формулами (§8.5–8.8 из
   POLYLINEARC.md).

### 6.3. Влияние на критичные механизмы

* **Постоянная ширина:** строится **точно** как кольцевой сектор — главное преимущество варианта
  (нет гранёности на любом зуме без перетесселяции).
* **Переменная ширина:** всё равно требует тесселяции (точного простого представления нет,
  POLYLINEARC.md §4.4) — здесь вариант B не лучше A.
* **Контуры/заливка:** структура `GLLWWidth.quad` (один четырёхугольник) **не описывает** дугу;
  нужна новая запись геометрии полосы (дуговая) либо набор quad. Это заметная переделка
  `Width3D_in_WCS_Array`/`DrawGeometry`.
* **Стыки:** самый дорогой пункт — miter по касательной и пересечение смещённых дуг
  (квадратные уравнения), круговая miter-цепочка для замкнутых (POLYLINEARC.md §4.5–4.6). Высокий
  риск.
* **Типы линий:** можно реализовать «честно» — раскладка по длине дуги, накопленная фаза, PLINEGEN
  (POLYLINEARC.md §5). Максимальное соответствие AutoCAD, но и максимум работы.

### 6.4. Преимущества

* Геометрическая точность (ширина-сектор, BBox, площадь, снапы центр/середина/квадранты).
* Корректный EXPLODE дуга→`GDBObjArc` (совместимость с AutoCAD, POLYLINEARC.md §6.3).
* Наилучшее долгосрочное соответствие поведению AutoCAD; «правильная» архитектурная основа.
* Точные измерения (длина, площадь) без зависимости от тесселяции.

### 6.5. Недостатки и риски

* **Максимальный объём нового кода** в самой рискованной зоне (стыки дуга↔дуга, выворот внутренней
  границы) — именно те пункты, которые POLYLINEARC.md §9.3 относит к высокому риску.
* Требуется новая модель геометрии полосы (замена/расширение `quad`-модели).
* Высокая цена ошибки: дефекты в стыках/заливке заметны визуально и трудно отлаживаются.
* Длинный путь до первого видимого результата (много инфраструктуры до первого корректного кадра).

### 6.6. Влияние на производительность

Отрисовка постоянной ширины эффективнее (меньше примитивов, точные дуги), но построение стыков
дороже (аналитические пересечения). В сумме — сопоставимо, с лучшим качеством на высоких зумах.

### 6.7. Поэтапный план

* **Этап B0 — фундамент данных (round-trip).** Идентичен A0.
* **Этап B1 — модуль геометрии bulge.** Цель: формулы дуги с юнит-тестами. Сделать: центр, R, углы,
  длина, точка, касательная, BBox. Результат: проверяемые формулы. Критерий: совпадение с числовым
  примером POLYLINEARC.md §3.5 (R=431.13, θ=126.865°, центр (1535.78,197.17)).
* **Этап B2 — тонкая дуга + измерения.** Цель: дуга как примитив. Сделать: ветвление осевой
  отрисовки, точные BBox/площадь/снапы, EXPLODE→`GDBObjArc`. Результат: дуга «живёт» в полилинии.
  Критерий: снап к центру/середине дуги, корректная площадь замкнутой фигуры с дугой.
* **Этап B3 — постоянная ширина (сектор).** Цель: точная толстая дуга. Сделать: концентрические
  дуги + торцы + защита от выворота. Результат: кольцевой сектор с заливкой. Критерий: совпадение с
  AutoCAD на тесте «дуга + постоянная ширина».
* **Этап B4 — переменная ширина + стыки.** Цель: общий случай. Сделать: тесселяция переменной
  ширины, miter по касательной, пересечение смещённых дуг, круговая цепочка для замкнутых.
  Результат: произвольные толстые полилинии с дугами. Критерий: отсутствие разрывов/заломов на
  наборе тестов из POLYLINEARC.md §10.3.
* **Этап B5 — типы линий по дуге.** Цель: точный Linetype. Сделать: раскладка по длине дуги,
  накопленная фаза, PLINEGEN. Результат: соответствие AutoCAD. Критерий: непрерывность фазы
  DASHED/CENTER через дуги и вершины.

## 7. Вариант C — гибридный (аналитическое хранение + тесселяция при построении ширины)

### 7.1. Основная идея

Совместить сильные стороны A и B: **данные и измерения — аналитическая дуга** (как в B), а
**построение ширины/заливки — через тесселяцию в существующий quad-конвейер** (как в A). То есть
дуга остаётся «настоящей» для хранения, снапов, BBox, площади, длины (Linetype) и EXPLODE, но в
момент построения полосы ширины она адаптивно (по LOD) превращается в подсегменты, которые проходят
через нетронутый `CalcWidthSegment`/miter/`DrawGeometry`.

### 7.2. Принцип работы

1. Хранение: vertex + bulge (общий фундамент). Дополнительно — кэш аналитических параметров дуги
   (центр, R, углы) на сегмент, считается в `FormatEntity`.
2. Измерения и сервис: BBox, площадь, длина, снапы (центр/середина/квадранты), EXPLODE→`GDBObjArc`
   — по аналитической дуге (модуль формул, как в B1/B2). Это даёт «правильное» поведение редактора
   без тяжёлой геометрии ширины.
3. Построение ширины: в `createpoint` дуговые сегменты тесселируются в подсегменты с
   интерполированной шириной и передаются в существующий `CalcWidthSegment` (как в варианте A).
   Никакой новой математики кольцевого сектора и пересечения смещённых дуг — стыки решаются на
   уровне подсегментов.
4. Типы линий: осевая линия рисуется через `DrawPolyLineWithLT` по тесселированной ломаной;
   поскольку шаг тесселяции адаптивен, раскладка по длине ломаной ≈ по длине дуги. При желании
   фазу можно скорректировать по точной аналитической длине дуги (есть из п.2).

### 7.3. Влияние на критичные механизмы

* **Постоянная ширина:** через тесселяцию (как A) — приближённо, но адаптивно по LOD (визуально
  гладко). Точного сектора, как в B, нет; при необходимости его можно добавить позже точечно, не
  ломая остальное.
* **Переменная ширина:** через тесселяцию — естественно и корректно (как A).
* **Контуры/заливка:** существующий quad-конвейер без изменений.
* **Стыки:** решаются на уровне подсегментов существующим miter — без аналитических пересечений
  дуг (главное упрощение против B).
* **Типы линий:** длина дуги доступна аналитически → раскладка штрихов точна по фазе; геометрия
  штрихов — по тесселированной ломаной (визуально корректно).
* **Снап/BBox/площадь/EXPLODE:** аналитически точные (как B) — снимает главные недостатки A.

### 7.4. Преимущества

* Убирает основные минусы A (точные снапы, BBox, площадь, EXPLODE→`ARC`).
* Избегает самой рискованной части B (аналитические стыки дуга↔дуга, кольцевой сектор, выворот) —
  они заменяются тесселяцией.
* Переиспользует **и** тесселяцию bulge (4.1), **и** LOD (4.2), **и** формулы `GDBObjArc` (4.3),
  **и** `DrawPolyLineWithLT` (4.4).
* Хороший баланс «риск/качество/срок»; раннее получение видимого результата (после фундамента и
  тесселяции), при этом «правильная» модель данных сразу.
* Оставляет дверь открытой: точный кольцевой сектор (из B) можно внедрить позже как оптимизацию
  рендера, не меняя модель данных и I/O.

### 7.5. Недостатки и риски

* Две представления дуги (аналитическое + тесселированное) нужно держать согласованными; требуется
  отображение «индекс исходного сегмента → диапазон подсегментов» для интерполяции ширины и
  корректного miter на границах исходных сегментов.
* Ширина на дуге всё ещё аппроксимация (как A) — для предельной точности на печати может
  потребоваться поднять `N` или добавить сектор из B.
* Чуть больше кода, чем в A (аналитический слой измерений), но существенно меньше, чем в B.

### 7.6. Влияние на производительность

Сопоставимо с A по построению ширины (тесселяция), плюс лёгкий аналитический слой измерений
(дёшев). Хорошо масштабируется через адаптивный `N` и `simplydraw`.

### 7.7. Поэтапный план

* **Этап C0 — фундамент данных (round-trip).** Идентичен A0/B0.
* **Этап C1 — аналитический слой дуги.** Цель: «правильные» данные дуги. Сделать: модуль формул
  bulge (как B1) + кэш параметров сегмента; точные BBox/площадь/длина/снапы; EXPLODE→`GDBObjArc`.
  Результат: редактор «понимает» дугу. Критерий: совпадение с примером POLYLINEARC.md §3.5; снап
  центра/середины дуги.
* **Этап C2 — тесселяция для осевой и ширины.** Цель: видимые толстые дуги. Сделать: адаптивная
  тесселяция дугового сегмента в подсегменты с интерполированной шириной → существующий
  `CalcWidthSegment`/`DrawGeometry`; связь «исходный сегмент → подсегменты». Результат: постоянная и
  переменная ширина на дуге рисуются и заливаются. Критерий: отсутствие разрывов на стыках,
  гладкость на разных зумах.
* **Этап C3 — типы линий.** Цель: Linetype с точной фазой. Сделать: осевую отрисовку через
  `DrawPolyLineWithLT`, фаза по аналитической длине дуги; PLINEGEN. Результат: корректные штрихи по
  дуге. Критерий: непрерывность фазы DASHED/CENTER через дуги/вершины.
* **Этап C4 (опционально) — точный сектор.** Цель: точность печати. Сделать: для постоянной ширины
  заменить тесселяцию кольцевым сектором (заимствуя B3) только в рендере. Результат: безгранная
  толстая дуга. Критерий: совпадение с AutoCAD на печати без зависимости от `N`.

## 10. Рекомендация

**Рекомендуется вариант C (гибридный) с обязательным общим фундаментом (этап *0) и возможностью
последующего точечного перехода к точному сектору варианта B.**

Обоснование с точки зрения архитектуры ZCAD:

1. **Соответствие уже существующему разделению в коде.** Класс `GDBObjLWPolyline` уже разделяет
   «исходную» геометрию (`Vertex2D_in_OCS_Array` + параллельный `Width2D_in_OCS_Array`) и
   «производную» (`Vertex3D_in_WCS_Array`, `Width3D_in_WCS_Array`). Гибрид встаёт ровно в эту
   модель: bulge — ещё один параллельный массив исходных данных, тесселяция — производная
   геометрия. Никакой ломки несущей структуры.

2. **Минимизация работы в зоне наибольшего риска.** POLYLINEARC.md §9.3 относит к высокому риску
   именно стыки дуга↔дуга, выворот внутренней границы и аналитический Linetype. Вариант C обходит
   первые два, сводя их к существующему miter между подсегментами, и решает Linetype через уже
   готовый `DrawPolyLineWithLT` с точной фазой по аналитической длине. Это убирает большую часть
   технического риска при сохранении корректного поведения редактора.

3. **Максимальное переиспользование.** Вариант C задействует все четыре найденных «готовых»
   механизма: тесселяцию bulge из `uzeboundarypath.pas` (§4.1), адаптивный LOD из
   `GDBObjArc.createpoints` (§4.2), формулы/снапы дуги из `GDBObjArc` (§4.3) и LT-раскладку
   `DrawPolyLineWithLT` (§4.4). Это сокращает объём *нового* кода относительно варианта B при
   сохранении его ключевых преимуществ (точные снапы/BBox/площадь/EXPLODE).

4. **Правильная модель данных сразу, оптимизация — потом.** В отличие от варианта A, гибрид с
   первого этапа хранит дугу аналитически, поэтому переход к точному кольцевому сектору (этап C4,
   заимствование B3) — это локальная оптимизация рендера, не затрагивающая I/O, снапы и измерения.
   Это снижает стоимость будущего повышения качества и оставляет путь к полному варианту B
   эволюционным, без переписывания.

5. **Ранний работающий результат.** Уже после фундамента (C0) обеспечивается round-trip без потерь;
   после C1–C2 — видимые толстые дуги с корректными снапами; после C3 — типы линий. Каждый этап
   даёт самостоятельную ценность и проверяемый критерий завершения.

**Если приоритет проекта — максимальная точность печати и полное соответствие AutoCAD прямо
сейчас** (а не эволюционно), оправдан вариант B, но с осознанием высокого риска и большего срока.
**Если нужен только быстрый визуальный результат без требований к снапам/EXPLODE/измерениям** —
достаточно варианта A. Гибрид C выбран как баланс, наиболее согласованный с текущей архитектурой
ZCAD и с выводами POLYLINEARC.md.

Во **всех** вариантах первым шагом выполняется общий фундамент (этап *0): хранение bulge, чтение
и запись кода 42 в DXF, перенос bulge из DWG, тесселяция bulge в proxy-объектах. Этот шаг
наименее рискован, не зависит от выбора варианта и сразу устраняет текущую потерю данных
(POLYLINEARC.md §9.1–9.2).
