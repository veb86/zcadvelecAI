# Отчёт по модулю SHXTOPDF

> **Цель отчёта:** дать полное описание работы модуля `cad_source/zcad/velec/SHXTOPDF`,
> определить, **что уже реализовано**, **что ещё требуется доделать**,
> оценить **сложность задачи** и **трудозатраты**.
>
> Отчёт подготовлен на основании чтения исходных файлов `.pas` в ветке
> `issue-1008-f40644d70bf7`. Все оценки привязаны к конкретным файлам и строкам.
>
> **Задача из Issue #1008:** построить «ПОЛНЫЙ PDF EXPORT ENGINE» для ZCAD,
> внутри которого SHX-текст — лишь одна из веток (наравне с геометрией,
> hatch, растровыми изображениями). Настоящий отчёт фиксирует,
> **в какой точке этого пути сейчас находится код**.

---

## 1. Место модуля в общей задаче

Согласно постановке Issue #1008, речь идёт не о «печати SHX», а о построении
собственного движка экспорта чертежа в PDF:

```
CAD сцена
   ↓
[Разбор объектов]
   ↓
Dispatcher
   ├── Geometry  → PDF path      (m l c S)
   ├── Text SHX  → Type3 + Tj    ←── текущий модуль SHXTOPDF
   ├── Text TTF  → Tj (embedded TTF)
   ├── Images    → XObject       (/Im Do)
   └── Hatch     → fill paths    (f)
   ↓
PDF Page Content
   ↓
PDF Writer
```

Папка `cad_source/zcad/velec/SHXTOPDF/` закрывает **только ветку «Text SHX»**
полного движка. Всё остальное (линии, дуги, заливки, изображения, PDF Writer,
диспетчер объектов сцены) в кодовой базе **отсутствует**.

Поиск по репозиторию показал следующее:

* строки `PDFExport`, `BeginPDF`, `pdfwriter`, `ExportToPDF` в `cad_source/`
  **не встречаются** ни в одном файле;
* строки `uzvshxtopdf*` встречаются **только** внутри папки `SHXTOPDF`
  и в `cad_source/zcad.pas` (подключение юнита `uzvshxtopdf_commandstart`,
  строка 289);
* никакие модули SHXTOPDF не используются из сторонних частей проекта.

Таким образом, модуль SHXTOPDF — это **изолированный конвейер**, подключённый
к CAD только в виде CLI-команд (`SHX_TO_PDF_READ`, `SHX_TO_PDF_TEST`,
`SHX_TO_PDF_TEST4`), но не встроенный ни в какой реальный экспорт чертежа.

## 2. Архитектура модуля (7 этапов)

Модуль спроектирован как семиэтапный конвейер. Архитектура — корректная,
модули разделены по ответственности, каждый этап имеет свой README,
свой набор типов и отдельный каталог `test/`:

## 3. Постатейный статус реализации

Оценки в колонке «Статус»:

* ✅ **Готово** — рабочая реализация, покрыта тестами.
* 🟡 **Частично** — код есть, но имеются пропуски, заглушки или упрощения.
* ❌ **Не реализовано** — тело функции — пустая заглушка или возвращает фиктивное значение.

### Этап 1 — SHXReader (парсер SHX)  — 🟡 **СКЕЛЕТ, НЕ ГОТОВ**

Файлы: `SHXReader/uzvshxtopdf_shxparser.pas` (526 строк),
`uzvshxtopdf_shxreader.pas`, `uzvshxtopdf_shxglyph.pas`,
`uzvshxtopdf_shxutils.pas`, `uzvshxtopdf_shxdebugsvg.pas`.

Реализовано:

* структура заголовка `TShxHeader`, открытие файла, `Reset/BlockRead`
  (строки 111–157);
* чтение таблицы смещений `ReadOffsetTable` (строки 160–191);
* обработчики команд `PenUp` (MoveTo), `PenDown` (LineTo), `Arc` —
  строки 211–306;
* диспетчер опкодов в `ParseGlyphCommands` (строки 309–383) с защитой
  от бесконечного цикла;
* функция `ParseGlyph`, вычисление `Bounds` и `AdvanceWidth`;
* экспорт глифов в SVG для отладки (`uzvshxtopdf_shxdebugsvg.pas`).

Критические пропуски:

* **В главной функции `Parse` (строка 502) стоит
  `SetLength(Result.Glyphs, 0);`.** Прочитанная таблица смещений
  (строки 483–501) **не используется**: цикл по глифам не запускается,
  `ParseGlyph` из `Parse` не вызывается. В итоге `Parse` **всегда
  возвращает шрифт с нулём глифов.** Это делает весь конвейер
  неработоспособным «из коробки» — все последующие этапы получают
  пустой вход.
* `ReadHeader` **не читает** настоящий заголовок SHX: имя шрифта берётся
  из имени файла (строка 140), `UnitsPerEm` жёстко равен `100`
  (строка 144). Реальная сигнатура `AutoCAD-86 shapes 1.0\n...\x1A`
  и поля из заголовка игнорируются.
* Поддерживаются только 5 опкодов: `PEN_UP=1`, `PEN_DOWN=2`, `ARC_CW=8`,
  `ARC_CCW=9`, `END=0` (строки 31–37). Все остальные коды спецификации
  SHX **не распознаются**:
  * `0x00` — конец формы (используется вместо `END=0` в реальных SHX);
  * `0x03`/`0x04` — изменение размера (divide/multiply vector);
  * `0x05`/`0x06` — push/pop позиции;
  * `0x07` — вложенный вызов sub-shape;
  * `0x0A` — oct-arc (8-октантное кодирование дуги);
  * `0x0B` — дробная дуга (fractional arc);
  * `0x0C`/`0x0D` — bulge arc, poly-arc;
  * `0x0E` — флаг «только вертикальный текст»;
  * старшие 4 бита опкода — короткая кодировка `direction + length`
    (`1..F` для направления, длина от 1 до 15).
* `ProcessArc` (строки 256–306) — **не декодирует** угловые байты
  SHX-формата: жёстко задаёт `StartAngle := 0; EndAngle := Pi/2`
  (строки 279–280). Комментарий на строках 282–283 прямо
  указывает: «упрощённая реализация».
* **BigFont (двухбайтовые коды)** не поддерживается. В комментариях
  SHXReader/README.md это помечено как Этап 2 дорожной карты.
* **Unifont / AutoCAD 2007 Unicode SHX** не поддерживается.
* Кодовая страница захардкожена 1251; автоопределение отсутствует.

Вывод: **реальный SHX файл этим парсером прочитан быть не может.** На
выходе будет либо пустой шрифт, либо обрывочные LineTo-команды и
декоративные дуги фиксированной геометрии.

### Этап 2 — ApproGeom (аппроксимация геометрии)  — ✅ **ГОТОВО**

Файлы: `approgeom/uzvshxtopdfapprogeom.pas`, `…arc.pas` (457 строк),
`…stroke.pas`, `…types.pas`, `…settings.pas`.
Тесты: `approgeom/test/` (`…testarc.pas`, `…testerror.pas`,
`…testrender.pas`).

Реализовано полностью и корректно:

* вычисление коэффициента `k = 4/3 * tan(θ/4)` для аппроксимации дуги
  кубической кривой Безье (строки 124–146 в `…arc.pas`);
* разбиение дуги на сегменты при угле > 90° (строки 348–357);
* контрольные точки через касательные в начальной и конечной точках
  дуги (строки 260–270);
* обработка отрицательного радиуса через отражение (строки 274–286);
* полная аппроксимация окружности (строки 394–455, по умолчанию 4
  сегмента);
* защита от некорректных входных данных: `NaN`, `Infinity`, нулевой
  радиус, дуга < допуска (строки 310–323).

В README модуля (`approgeom/README.md`) приведены ссылки на
математические источники (Riškus 2006; Dokken 1990). Код соответствует.

Замечания:

* режим «Expand Stroke» (превращение stroke в замкнутые fill-контуры с
  соединениями и окончаниями) описан в README, но в коде реализован
  минимально — по-настоящему понадобится только при экспорте заливок;
* stroke-only путь самодостаточен и покрывает штатный случай SHX-шрифтов
  (все SHX-формы — однопиксельные контуры).

### Этап 3 — Transform (матричные трансформации)  — ✅ **ГОТОВО**

Файлы: `transform/uzvshxtopdftransform.pas`, `…types.pas`,
`…matrix.pas` (352 строки), `…apply.pas`, `…align.pas`.
Тесты: `transform/test/` (unit + matrix + pdf).

Реализовано полностью:

* единичная матрица, scale, rotate, translate, shear, mirror X/Y
  (строки 211–262 в `…matrix.pas`);
* перемножение матриц 3×3 (строки 271–284), применение к точке
  (строки 287–291);
* определитель и обратная матрица с обработкой вырожденного случая
  `|det| < 1e-10` (строки 293–344);
* конверсии градусы↔радианы, проверка тождественности матрицы.

Порядок применения трансформаций (README: «нормализация → height →
widthFactor → oblique → mirror → rotation → alignment → translate →
kerning») реализован в `uzvshxtopdftransformapply.pas`.
Выравнивания `alLeft/alCenter/alRight`, `alTop/alBaseline/alBottom`
есть в `uzvshxtopdftransformalign.pas`.

Замечания: при большом количестве глифов возможна оптимизация (склейка
матриц в одну до применения к точкам), но функционально этап закрыт.

### Этап 4 — CharProcs (PDF-потоки глифов)  — ✅ **ГОТОВО**

Файлы: `charprocs/uzvshxtopdfcharprocs.pas`, `…writer.pas` (352 строки),
`…font.pas`, `…bbox.pas`, `…types.pas`.
Тесты: `charprocs/test/` (count, font, widths, pdf).

Реализовано:

* корректное форматирование числа для PDF с обрезкой концевых нулей и
  точки (строки 141–175 в `…writer.pas`);
* превращение безьевого сегмента в PDF-оператор: эвристика «прямая
  линия» по близости контрольных точек к отрезку (строки 179–220);
  используется `l` для линий, `c` для кривых, `m` для MoveTo;
* генерация CharProc с обёрткой `q … S/f … Q`, с bounding box для
  оператора `d1` (строки 297–350);
* сборка `/Type /Font /Subtype /Type3` объекта с FontMatrix
  `[1 0 0 1 0 0]` (мировые координаты уже применены на Этапе 3),
  массива `/Widths`, словаря `/CharProcs`, `FirstChar`, `LastChar`
  (`uzvshxtopdfcharprocsfont.pas`);
* интеграционный тест `uzvshxtopdfcharprocstestpdf.pas` пишет
  тестовый PDF-файл.

Это самая сильная часть модуля — код действительно соответствует
формату Type3 Font из спецификации PDF 1.7 §9.6.4.

### Этап 5 — CMap (ToUnicode)  — ✅ **ГОТОВО**

Файлы: `cmap/uzvshxtopdfcmap.pas`, `…writer.pas` (408 строк),
`…mapping.pas`, `…types.pas`.
Тесты: `cmap/test/` (mapping, duplicate, stream).

Реализовано:

* полная шапка CMap с `CIDSystemInfo`, `CMapName`, `CMapType 2`;
* `codespacerange` с поддержкой одно- и двухбайтового диапазонов;
* блоки `bfchar` с соблюдением ограничения **100 записей на блок**
  (PDF §9.10.3), автоматическое разбиение на несколько блоков;
* нижний регистр hex, Unicode BMP (U+0000..U+FFFF);
* таблицы CP1251, CP866, ASCII, автоопределение локали (`mlAuto`);
* валидация: `ValidateToUnicodeCMap` сверяет коды из CharProcs с
  записями в CMap.

Ограничения:
* без суррогатных пар (символы > U+FFFF) — это соответствует
  потребностям CAD-текста;
* BigFont/Unifont (двухбайтовые SHX-коды) сейчас не приходят с
  Этапа 1 — после доработки Этапа 1 может потребоваться
  дополнительный тест.

### Этап 6 — SubCaching (кеш и субсет)  — 🟡 **ПАМЯТЬ — ДА, ДИСК — НЕТ**

Файлы: `subcaching/uzvshxtopdfsubcache.pas`,
`…subset.pas`, `…hash.pas`, `…types.pas`, `…disk.pas` (369 строк).
Тесты: `subcaching/test/` (dup, hash, subset).

Реализовано (в памяти):

* ключ кеша: имя шрифта + код глифа + `Height` + `WidthFactor` +
  `ObliqueDeg`;
* хеширование FNV-1a 64-bit;
* дедупликация CharProc: 1000 одинаковых символов → 1 CharProc
  (проверено тестом);
* субсет глифов: метка использованных, построение итогового subset с
  `FirstChar/LastChar/Widths`.

Не реализовано (явные заглушки):

* в `uzvshxtopdfsubcachedisk.pas`:
  * `LoadCacheFromDisk` (строки 250–282) — возвращает `False`,
    в логе пишет «функция не реализована»;
  * `SaveCacheToDisk` (строки 285–317) — возвращает `False`;
  * `IsDiskCacheAvailable` (строки 320–330) — всегда `False`;
  * `ClearDiskCache` (строки 333–356) — только лог;
  * `GetDiskCacheSize` (строки 359–367) — всегда `0`.

Планируемый формат дискового кеша описан в README, но ни бинарный
формат, ни версионирование, ни инвалидация по модификации `.shx` —
не написаны. Для первого релиза это не критично.

### Этап 7 — GenInteg (интеграция с PDF)  — 🟡 **ВНУТРИ МОДУЛЯ — ДА, С ZCAD — НЕТ**

Файлы: `geninteg/uzvshxtopdfgeninteg.pas` (562 строки), `…fontbind.pas`,
`…textwriter.pas`, `…escape.pas`, `…types.pas`.
Тесты: `geninteg/test/` (escape, font, text).

Реализовано:

* класс `TPdfIntegrator` (строки 81–211) собирает запросы
  `AddTextRequest(TextParams)`, обрабатывает их, связывает со шрифтами;
* расчёт матрицы текста (rotation + scale + oblique) — строки
  365–387;
* генерация PDF-текстового блока `BT … Tf … Tm … Tj … ET` через
  `uzvshxtopdfgenintegtextwriter.pas`;
* экранирование `(`, `)`, `\` и непечатных символов в строках PDF —
  `uzvshxtopdfgenintegescape.pas`;
* управление привязкой шрифтов к ресурсам страницы —
  `uzvshxtopdfgenintegfontbind.pas`;
* словарь ресурсов `/Font << /F1 … >>` и сбор content-stream.

Что отсутствует:

* **Сам PDF Writer.** `TPdfIntegrator` строит фрагменты content-stream
  и ссылки на объекты шрифтов, но **не пишет PDF-файл**: нет
  cross-reference table, trailer, потока страниц, объектных словарей,
  сжатия FlateDecode.
* **Диспетчер объектов CAD-сцены.** Интегратор ожидает на вход уже
  готовые `TextParams`; код, который обойдёт `TDrawing` и
  сформирует эти запросы для каждого текстового объекта, в модуле
  отсутствует. В `uzvshxtopdf_commandstart.pas` есть только
  *сбор кодов выделенных символов* (`CollectUsedChars`,
  строки 161–218) — этого мало.
* **Невербальные ветки pipeline** (геометрия, hatch, изображения),
  которые по постановке Issue должны сосуществовать с SHX-текстом в
  одном content-stream, **в репозитории отсутствуют**.

## 4. CAD-команды, которые реально сейчас работают

Из `uzvshxtopdf_commandstart.pas`:

* `SHX_TO_PDF_READ <path>` — открывает SHX-файл, пытается распарсить
  (получит 0 глифов из-за Этапа 1), создаёт каталог `shx_debug/`,
  запускает `ExportFontToSVG` и `ApplyStage2`. Реальный результат сейчас —
  каталог `shx_debug/` с пустым `font_overview.svg` и предупреждениями
  «Шрифт не содержит глифов».
* `SHX_TO_PDF_TEST` — запускает unit-тесты Этапа 2 (arc + numerical
  stability). Эти тесты проходят, так как Этап 2 сделан и проверяется
  на синтетических данных.
* `SHX_TO_PDF_TEST4` — запускает 4 теста Этапа 4 (count, font, widths,
  pdf integration).

Никаких других точек входа нет.

Итого **конвейер SHX-текста** — около 65 % готовности по модулям;

поскольку вход конвейера (Этап 1) отдаёт пустой массив глифов.

**«Полный PDF Export Engine»** из постановки Issue #1008 —
готовность порядка **15–20 %**, так как у проекта нет:

* PDF Writer (объектная запись, xref, trailer, FlateDecode);
* обходчика сцены CAD и диспетчера объектов;
* конвертеров геометрии, hatch, изображений;
* интеграции с существующим экспортом/принтером ZCAD.

## 7. Что требуется сделать (roadmap)

### 7.1. Минимальный рабочий SHX-текст в PDF (MVP)

Цель: экспорт текстовой надписи SHX в валидный PDF с корректным Type3
Font и ToUnicode.

1. **Этап 1 — Дописать SHX-парсер до рабочего состояния.**
   * Реализовать настоящее чтение заголовка (`AutoCAD-86 shapes 1.0`,
     версии 1.0/1.1/2.0, признак `shapes`/`bigfont`/`unifont`).
   * Запустить цикл по таблице смещений внутри `Parse`, вызывать
     `ParseGlyph` для каждой записи.
   * Добавить все опкоды согласно спецификации: `0x00..0x0E`, а также
     короткий формат «direction(0..F) + length(1..F)» в одном байте.
   * Реализовать `0x0A` (oct-arc) и `0x0B` (fractional arc) с реальным
     декодированием стартового/конечного октантов.
   * Опционально: BigFont и Unifont (двухбайтовые коды).
2. **Этап 7 — Написать PDF Writer** для SHX-случая: объект-словарь,
   cross-reference table, trailer, `stream/endstream` с FlateDecode.
3. **Связать `TPdfIntegrator` с настоящим CAD-проходом** — итерация по
   выделенному тексту (или всем text-entity) с извлечением
   TextStyle → SHX-файла.
4. **Интеграционные тесты:** экспортировать `A`, `1`, `Б` (CP1251)
   simplex.shx в PDF, открыть в Adobe Reader, проверить копирование
   текста (`pdftotext`).

### 7.2. «Полный PDF Export Engine» (по постановке Issue)

Помимо MVP потребуется:

5. **Диспетчер объектов сцены.** Обход `TDrawing`, диспатч по типу:
   line/arc/polyline/text/hatch/image.
6. **Geometry backend.** Конвертация `m l S`, `c` (Безье), `w`
   (толщина), `RG/rg` (цвет) — отдельный модуль, аналог ApproGeom
   для всех геометрических примитивов.
7. **Hatch backend.** Заливка через `f` / `f*` с even-odd правилом.
8. **Image backend.** `XObject` `/Subtype /Image`, DCTDecode для JPEG,
   FlateDecode для растров. Отдельная проблема — цветовые пространства.
9. **TTF backend.** Для не-SHX-текста: встраивание TTF (`/FontFile2`),
   либо base14-шрифты.
10. **Layout/viewport.** Многостраничные PDF, масштабирование, рамки
    листа, штампы.

## 8. Оценка трудозатрат

Оценки ниже приведены в «человеко-часах» разработчика, знающего формат
SHX и спецификацию PDF, и уже ориентирующегося в кодовой базе ZCAD.
Для менее опытного разработчика умножайте на 1.5–2.

### 8.1. Доведение текущего конвейера SHX до работоспособности (MVP)

| Задача | Часы |
|--------|------|
| Этап 1: реальный разбор заголовка SHX | 4 |
| Этап 1: запуск цикла глифов из `Parse`, связка с `ParseGlyph` | 4 |
| Этап 1: реализация опкодов 0x00–0x0E и короткой формы направлений | 16 |
| Этап 1: oct-arc / fractional arc (реальная геометрия) | 8 |
| Этап 1: BigFont / Unifont | 12 |
| Этап 1: тесты на реальных `simplex.shx`, `romans.shx`, `txt.shx` | 4 |
| Этап 7: простейший PDF Writer (один текст на странице) | 16 |
| Этап 7: обход text-entity из CAD + извлечение SHX-файла по стилю | 8 |
| Интеграционные тесты (Adobe Reader, pdftotext, pdffonts) | 6 |
| Багфиксы, документация | 6 |
| **Итого MVP** | **≈ 84 часа (2 недели)** |

Без BigFont/Unifont — около **70 часов** (≈ 1.5 недели).

### 8.2. Полный PDF Export Engine

К MVP сверху добавляется:

| Задача | Часы |
|--------|------|
| Полноценный PDF Writer (xref, trailer, компрессия, многостраничность) | 24 |
| Диспетчер объектов сцены | 16 |
| Geometry backend (line/arc/polyline + w, RG/rg) | 24 |
| Hatch backend | 16 |
| Image backend (JPEG/PNG → XObject) | 24 |
| TTF backend (embedded TrueType) | 24 |
| Layout / viewport / штампы | 24 |
| Subcaching: дисковый кеш (опц.) | 12 |
| Тесты, сверка с эталонными PDF | 16 |
| Интеграция с существующим меню «Печать/Экспорт» ZCAD | 8 |
| **Итого «полный движок»** | **≈ 188 часов сверху MVP** |

Общий бюджет «от нуля до работающего движка»: **≈ 270 часов**
(≈ 7 рабочих недель одного разработчика fulltime).

### 8.3. Сложность

* **Этапы 2, 3, 4, 5** — средняя сложность, классическая геометрия и
  чтение спецификации PDF; сделано и закрыто.
* **Этап 1 (SHX parser)** — высокая сложность. Формат SHX плохо
  документирован, существуют разные версии (1.0/1.1/2.0), есть
  производные (BigFont, Unifont). Потребуется сверка с
  open-source парсерами (LibreDWG, ezdxf) и ручной reverse engineering.
* **Этап 7 и «Geometry/Hatch/Image» backends** — средне-высокая
  сложность; много мелких деталей PDF-спецификации, легко получить
  невалидный файл, который откроется только в некоторых viewer'ах.
* **PDF Writer** — отдельная инженерная задача; альтернатива —
  подключить готовую Pascal-библиотеку (fcl-pdf из FPC, PDF4Laz,
  SynPDF), если это допустимо лицензионно. Это сократит оценку
  PDF Writer с 24 ч до 4–6 ч адаптации.

## 9. Рекомендации

1. **Сначала закрыть Этап 1.** Без работающего парсера все остальные
   этапы (даже идеально написанные) бесполезны. Для быстрого выхода
   в рабочее состояние — реализовать минимум: базовый набор опкодов
   + корректный заголовок + реальный запуск парсинга из `Parse`.
   Без этого дальше двигаться смысла нет.
2. **Рассмотреть `fcl-pdf`** (FreePascal Component Library) как основу
   PDF Writer — это сильно упростит Этап 7 и последующее расширение на
   геометрию/hatch/images.
3. **Интеграционные тесты на реальных SHX** (`simplex.shx`, `romans.shx`,
   `txt.shx` из поставки AutoCAD/BricsCAD) — добавить в `approgeom/test/`
   или отдельный каталог `integration_tests/`; сейчас все тесты работают
   только на синтетических данных.
4. **Документировать ограничения** в README каждого этапа явным списком
   «что не поддерживается» — сейчас README описывают задуманную
   архитектуру, а не фактический статус.
5. **После закрытия Этапа 1** приоритет — MVP (SHX → PDF одной
   надписи), а затем уже расширение движка на геометрию и hatch.

## 10. Итог

* Архитектура модуля — **хорошая**: 7 этапов разделены по
  ответственности, есть README, тесты, логирование через `uzclog`.
* Этапы 2–5 реализованы **качественно** и соответствуют спецификации.
* Этап 1 (SHX parser) существует как **структурный скелет**, но
  в главной функции `Parse` отсутствует вызов цикла глифов, заголовок
  SHX не читается, большинство опкодов не поддерживается, углы дуг
  жёстко захардкожены. **По этой причине конвейер сейчас в целом не
  работоспособен.**
* Этап 6 — работает в памяти, дисковый кеш — заглушки.
* Этап 7 — строит фрагменты content-stream, но PDF-файл **не пишет**.
* Интеграции с CAD-экспортом **не существует** (и самого PDF-экспорта
  в ZCAD тоже).

Оценка трудозатрат:

* **MVP (одна SHX-надпись → валидный PDF):** ≈ 70–84 часа.
* **Полный PDF Export Engine, как описано в Issue #1008:**
  ≈ 270 часов (~ 7 недель fulltime).

Основные блокеры, которые нужно снять в первую очередь:

1. `Parse` в `uzvshxtopdf_shxparser.pas:502` должна реально парсить
   глифы.
2. Должен появиться настоящий PDF Writer (свой или на базе `fcl-pdf`).
3. Должен появиться проход по сцене CAD, который превращает
   текстовые объекты в `TextParams` для `TPdfIntegrator`.

Без этих трёх пунктов все корректно сделанные этапы 2–5 работают
«вхолостую».
