# Архитектура системы парсинга прокси-объектов DXF

## Проблема
Прокси-объекты в DXF (например, `SPDSPOLYMORPHMARK`, `ACAD_PROXY_ENTITY`) хранят геометрию в бинарном формате (код DXF 310). Разные типы объектов имеют разную структуру данных.

## Решение
Модульная система парсеров, где каждый тип объекта имеет свой парсер, знающий структуру данных.

## Структура модулей

```
uzeentproxyparser.pas    - Базовая система парсинга
  ├── TProxyDataReader   - Базовый класс для чтения бинарных данных
  ├── TProxyCircleReader - Парсер кругов
  ├── TProxyLineReader   - Парсер отрезков
  └── TProxySPDSMarkReader - Парсер СПДС маркеров

uzeentproxytypes.pas     - Типы данных прокси-объектов
  ├── TProxyCircleData   - Данные круга
  ├── TProxyLineData     - Данные отрезка
  ├── TProxyTextData     - Данные текста
  └── TProxySPDSMarkData - Данные СПДС маркера

uzeentproxydraw.pas      - Отрисовка прокси-объектов
  ├── DrawProxyObject    - Главная функция отрисовки
  ├── DrawProxyCircle    - Отрисовка круга
  └── DrawProxySPDSMark  - Отрисовка СПДС маркера

uzeentacdproxy.pas       - Основной прокси-объект ZCAD
  └── GDBObjAcdProxy     - Объект, загружаемый из DXF
```

## Структура данных СПДС маркера

### Текстовые данные (коды DXF 300, 301, 40, 90)
```
301: Name
300: 9
301: Info
300: Позиционный маркер
301: Scale
 40: 100.0
301: Shape
300: Окружность
301: Text
300: 9
301: Text height
 40: 3.5
301: Text style
300: ГОСТ 2.304
```

### Бинарные данные (код DXF 310)
```
Структура (позиции в байтах):
  [0-3]:   Размер данных (little-endian)
  [4-7]:   Версия формата
  [8-11]:  Смещение/количество записей
  [12-15]: Размер заголовка
  [16-19]: Дополнительные данные
  [20+]:   Данные объектов

Для круга:
  [252-259]:   Center X (double)
  [260-267]:   Center Y (double)
  [268-275]:   Center Z (double, обычно 0)
  [276-283]:   Radius (double)
```

## Алгоритм работы

1. **Загрузка из DXF** (`GDBObjAcdProxy.LoadFromDXF`):
   - Чтение кодов 92 (размер бинарных данных)
   - Чтение кодов 310 (бинарные данные)
   - Чтение кодов 300, 301, 40, 90 (текстовые/числовые данные)

2. **Определение типа объекта**:
   - По имени объекта (`SPDSPOLYMORPHMARK`, `ACAD_PROXY_ENTITY`)
   - По структуре бинарных данных

3. **Парсинг** (`TProxyDataReader`):
   - Выбор соответствующего парсера
   - Чтение бинарных данных
   - Извлечение геометрии

4. **Отрисовка** (`DrawProxyObject`):
   - Преобразование в объекты ZCAD (круг, линии, текст)
   - Отрисовка через стандартный механизм ZCAD

## Расширение системы

Для добавления поддержки нового типа объекта:

1. Создать класс-парсер, наследуясь от `TProxyDataReader`:
```pascal
TProxyArcReader = class(TProxyDataReader)
private
  FData: TProxyArcData;
public
  function CanRead: Boolean; override;
  procedure ReadData; override;
  property Data: TProxyArcData read FData;
end;
```

2. Реализовать `CanRead` - проверка структуры данных:
```pascal
function TProxyArcReader.CanRead: Boolean;
begin
  { Ищем характерные данные дуги }
  Result := (FBytesLen >= 80);  // Минимальный размер
  { Проверяем наличие center, radius, startAngle, endAngle }
end;
```

3. Реализовать `ReadData` - чтение данных:
```pascal
procedure TProxyArcReader.ReadData;
begin
  { Читаем center, radius, startAngle, endAngle }
  { Вычисляем BBox }
end;
```

4. Зарегистрировать парсер в фабрике

## Тестирование

Для тестирования парсеров:
1. Извлечь бинарные данные из DXF (код 310)
2. Создать парсер: `reader := TProxyCircleReader.Create`
3. Инициализировать: `reader.InitFromHex(hexData)`
4. Проверить: `if reader.CanRead then ...`
5. Прочитать: `reader.ReadData`
6. Использовать данные: `reader.Data`

## Известные проблемы

1. **Разные версии формата**: СПДС GraphiCS может использовать разные версии бинарного формата
2. **Отсутствие документации**: Структура данных определяется эмпирически
3. **Кодировка текста**: Текстовые данные могут быть в UTF-16 (код 310) или UTF-8 (код 300)
