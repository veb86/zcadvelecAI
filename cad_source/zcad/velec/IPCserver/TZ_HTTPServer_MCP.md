# ТЗ на развитие HTTPServer ZCAD для MCP

Подготовлено по [задаче #1476][issue], двум приведённым в ней анализам и исходникам
ZCAD после включения [анализатора стен][walls-pr]. Приоритеты и контракты ниже
предназначены для согласования. Строки, отмеченные как предложения, описывают
будущие возможности.

## Текущий контракт

- `HTTPStart 127.0.0.1 5000` запускает встроенный HTTPServer. `GET /ipc` проверяет
  доступность HTTP, а `POST /ipc` принимает `{id, cmd, args, token?}`. Успех содержит
  `{id, status:"ok", result?:string}`, ошибка команды обычно приходит с HTTP 200
  и полем `error` в конверте. Пустое тело даёт HTTP 400. Маршрутизация и логирование
  находятся в [uzvhttpserver.pas](uzvhttpserver.pas).
- [Диспетчер](uzvhttpipc.pas) нормализует имя команды, находит обработчик,
  копирует аргументы в очередь и ждёт событие до 30 секунд. Обработчик выполняется
  в [GUI idle](../../gui/uzcmainform.pas). При таймауте ожидающий HTTP-поток
  освобождает свою ссылку. Команда остаётся в очереди или уже выполняется,
  поэтому её результат неизвестен клиенту. Сейчас очередь вычитывается целиком за
  один вызов idle, а повтор `id` сам по себе не устраняет повторное выполнение.
- Команды регистрируются через `RegisterHTTPIPCCommand` при инициализации unit.
  [Состав сборки](../../../zcad.pas) включает `LINE`, `CIRCLE`, `INSERT_DEV`
  и команды стен. `ARC` и `POLYLINE` зарегистрированы как заглушки.
  `uzvhttpcmdsystem`, `uzvhttpcmdfile`, `uzvhttpcmdtext` и `uzvhttpcmdbatch` здесь
  не подключены. Первые три используют устаревшее имя функции регистрации.
- HTTP-диспетчер сохраняет `token` без проверки. HTTPServer выставляет CORS `*`,
  записывает полные тела запросов и ответов в лог, а запросы ещё и в историю GUI.
  Текущий сценарий следует проверять на локальном `127.0.0.1`.
- [ZCAD_MCP_SERVER][mcp] уже предоставляет `zcad_health` и `zcad_execute`.
  Второй инструмент передаёт позиционные `args`, проверяет корреляцию `id` и
  возвращает конверт, сохраняя строковый `result`. По умолчанию мост ограничивает
  запрос 35 секундами, 1 МиБ для тела запроса и 8 МиБ для ответа. Есть конфигурация
  `allowedCommands`. Таймаут или разрыв соединения не повод автоматически
  повторять изменяющий вызов.

| Порядок | Что реализовать | Результат этапа |
| --- | --- | --- |
| 1 | Совместимость `/ipc` и надёжность | Рабочий `PING`, управляемая остановка, ограниченная очередь, журнал без тел |
| 2 | Сквозной обмен результатами анализатора стен | Клиент получает одобренную выборку, отправляет классификацию и видит итог подтверждения |
| 3 | Команды чтения чертежа | Сводка, выборка по страницам, выделение, геометрия и свойства по ссылке |
| 4 | Версионированный HTTP API | Discovery, задания и постраничное получение крупных результатов |

## 1. Совместимость и надёжность `/ipc`

1. Привести регистрацию system/file/text к `RegisterHTTPIPCCommand`. В
   поддерживаемую сборку добавить только `uzvhttpcmdsystem` с `PING`. Включение
   file/text/batch рассматривать отдельно после проверки их поведения, включая
   фактическую запись `SAVE`/`EXPORT` и общее состояние batch.
2. В `uzvhttpipc.pas` проверять форму `args` до создания команды и освобождать
   каждый объект на всех выходах, в том числе при исключениях парсинга, копирования
   и enqueue. Сохранить корреляцию `id`, существующий конверт и поведение таймаута
   `/ipc`. Ввести настраиваемые пределы тела, соединений и очереди. В GUI idle
   исполнять ограниченное число команд с бюджетом времени на проход. Для одной
   дорогой команды отдельно ограничить вход и объём работы.
3. При `HTTPStop` прекратить приём новых команд, разбудить ожидающих клиентов с
   определённым исходом для снятых с очереди команд и дать запущенным завершиться.
   Дождаться workers до освобождения сервера, очереди и блокировок, сохраняя
   возможность продвигать GUI. Проверить повторный `HTTPStart`.
4. Удалить запись тел из лога и истории GUI. Оставить выключенную по умолчанию
   диагностику метаданных (команда, корреляция, размер, время, итог), с исключением
   секретов и содержимого чертежа. Для сетевого доступа сначала согласовать
   аутентификацию, права на чтение и изменение, TLS и политику origin. Сохранить
   рабочие сценарии `/widgets`, `/grist` и отдельного TCP IPC.

Приёмка на работающем десктопном ZCAD включает `POST /ipc` с `PING` и совпадающим
`id` в ответе `result:"pong"`, незарегистрированную команду, ошибочные `args`,
параллельные запросы и `HTTPStop`/`HTTPStart` во время ожидания. Команда `npm run
smoke` из MCP проверяет путь через SDK и GUI без изменений в мосте. Существующий
[HTTP-тест с TFPHttpServer](../../../../experiments/issue1472/test_httpserver.mjs)
проверяет заголовки, маршруты и коды, а работу GUI и завершение workers проверяет
отдельный интеграционный сценарий.

## 2. Передача результатов анализатора стен

[PR #1475][walls-pr] уже решил передачу через `/ipc`. Дублировать анализатор и
создавать исходящий HTTP-запрос из ZCAD не требуется. MCP или другой внешний
клиент забирает данные по запросу и отправляет ответ. Выбор получателя и вызов
классификатора остаются у внешнего клиента. ZCAD управляет выборкой, предпросмотром,
проверкой классификации и созданием объектов.

| Шаг | Действующий вызов | Данные и переход |
| --- | --- | --- |
| Анализ | `WallAnalyze` в GUI или `WALL_ANALYZE [{window,min_thickness,max_thickness}]` | `candidate_preview`. Вместо `window` можно передать `handles`, без обоих используется выделение. |
| Статус | `WALL_PREVIEW []` или `[session_id]` | Идентификатор, фаза и счётчики текущей сессии. При отсутствии сессии пустой запрос возвращает `idle`. |
| Разрешение | `WallSend` в GUI | `approved_to_send` после просмотра кандидатов. |
| Получение | `WALL_SEND_AI [session_id]` | Только подтверждённые границы и оси, `candidate_id`, `source_handles`, толщина, координаты WCS. Фаза `awaiting_ai`. |
| Классификация | `WALL_AI_RESULT [response]` | Объект `{session_id,walls:[...]}`. ZCAD проверяет сессию, источники и поля результата, строит `recognition_preview` и возвращает сводку. |
| Применение | `WallCommit` или `WallCancel` в GUI | Создание полилиний одним Undo либо закрытие предпросмотра. `WALL_COMMIT` по HTTP запрашивает локальное подтверждение или возвращает итог завершённой сессии. `WALL_CANCEL [session_id]` отменяет сессию. |

Первую интеграцию выполнить с текущим `zcad_execute`, передавая, например,
`{"command":"WALL_SEND_AI","args":["{ECAFFC01-0FD2-44F9-A503-C1C8ED08E735}"]}`
после `WallSend` для реального `session_id`. Проверив `status`, клиент декодирует
JSON из `structuredContent.result` и передаёт классификатору полученный объект.
Классификацию следует отправлять как объект в `args[0]` команды `WALL_AI_RESULT`.
После локального подтверждения клиент запрашивает `WALL_PREVIEW [session_id]` и
получает `committed` и `created_count` для последней завершённой сессии. Контракт
кандидатов и пример ответа приведены в [README стен](skills/walls/README.md),
эталонный цикл показан в [wall_client.py](skills/walls/wall_client.py).

Доработки для MCP предлагается ограничить следующим:

- В [обработчиках стен](skills/walls/uzvhttpwallcommands.pas) сохранить привязку к
  чертежу и сессии, проверку исходной геометрии и обе точки подтверждения в GUI.
  Ввести пределы сегментов, пар и байтов до выдачи результата. При превышении
  вернуть явную ошибку с предложением сузить выборку. Пределы проверить с обеих
  сторон моста, в том числе для входящего результата классификатора.
- Сохранить `WALL_PREVIEW` для состояния и сводки. Для сценария, где клиенту
  нужны сами распознанные оси, предусмотреть `WALL_RESULT [session_id]` после
  показа результата и отдельного разрешения на выдачу. Возвращать только
  распознанные оси этой сессии с `candidate_id` и `confidence`. Большой результат
  выдавать страницами через этап 4, привязав его к владельцу и сессии. Закрытие
  предпросмотра, правка источников и закрытие чертежа отзывают доступ к этим данным.
- При появлении отдельных MCP tools декодировать и проверять схему результата
  в их регистраторах. `WALL_SEND_AI` меняет фазу сессии, а `WALL_PREVIEW` может
  обновить предпросмотр. Для обоих не объявлять `readOnlyHint:true`. После
  потери ответа проверять фазу через `WALL_PREVIEW` перед решением о повторе.

Взять небольшой DXF и внешний тестовый классификатор из
[десктопной проверки](skills/walls/test_wall_workflow.py), повторить сценарий
через MCP SDK. Проверить отказ до `WallSend`, получение только показанных
кандидатов, отказ при неверном `session_id`, переключении чертежа и правке
источников, показ результата без создания полилиний, локальные
`WallCommit`/`WallCancel`, проверку фазы после потери ответа, Undo и повторное
открытие сохранённого DXF. Для `WALL_RESULT`, если он нужен, проверить доступ
до и после разрешения, совпадение осей с предпросмотром, отзыв доступа и
превышение предела объёма.

## 3. Чтение чертежа (предлагаемый контракт)

Добавить `uzvhttpcmdquery.pas` и подключить его в `cad_source/zcad.pas`.
Проверять `drawings.GetCurrentDWG` и `GetCurrentROOT` до чтения. На первом этапе
запрашивать объекты верхнего уровня текущего `GetCurrentROOT^.ObjArray`, без
раскрытия блоков и временных объектов предпросмотра. Для фильтрации использовать
`GetObjType`, для выделения — `SelObjArray`, сопоставленный с тем же набором.
Геометрию читать через API конкретного типа, например `getCoordInWCS` у `LINE`
и `P_insert_in_WCS`/`Radius` у `CIRCLE`. Проверять доступность слоя, готовность
bbox и наличие `TVariablesExtender` перед обращением к этим данным.
Ориентиры — [uzcdrawings.pas](../../core/drawings/uzcdrawings.pas) и
[сбор данных стен](skills/walls/uzvhttpwallcollector.pas).

| Команда | `args` (`?` обозначает необязательное поле) | Данные в `result` после декодирования |
| --- | --- | --- |
| `QUERY_DRAWING_INFO` | `[]` | `drawingId`, `revision`, имя файла без пути, число объектов по типам |
| `QUERY_OBJECTS` | `[{type?,limit?,offset?,drawingId?,revision?}]` | `drawingId`, `revision`, `objects`, `nextOffset`. Запись включает `objectId`, `handle`, `type`, `layer`, `bbox`, `selected`. |
| `QUERY_SELECTION` | `[{limit?,offset?,drawingId?,revision?}]` или `[]` | Та же страница для выделенных объектов текущего пространства |
| `QUERY_OBJECT` | `[{drawingId,objectId}]` или `[{drawingId,handle}]` | Общие поля и `geometry` в WCS для поддерживаемого типа. Начать с `LINE` и `CIRCLE`. |
| `QUERY_PROPERTIES` | `[{drawingId,objectId,limit?,offset?,revision?}]` или ссылка с `handle` вместо `objectId` | Страница разрешённых переменных с именами и строковыми значениями, `revision` и `nextOffset`. Для объекта без extender список пуст. |

- `objectId` — непрозрачный идентификатор в рамках открытого чертежа, в том числе
  для объектов, созданных в текущей сессии. Поддерживать его через жизненный цикл
  сущности. `handle` — строка DXF при наличии уникального ненулевого
  `PExtAttrib^.dwgHandle`, иначе `null`. Проверить назначение DXF handle при
  создании, сохранении и повторном открытии. Временные ссылки стен относятся
  только к их `session_id`. Указатели и индексы обхода наружу не выдавать.
- Предложение для начала — `limit=100`, максимум 1000, `offset=0`. Продолжение
  передаёт тот же фильтр, `drawingId`, `revision` и `nextOffset`. Помечать revision
  устаревшей при изменении набора, свойств или выделения, от которых зависит
  ответ. На последней странице `nextOffset:null`. При смене чертежа или revision
  клиент начинает выборку заново. Предел страницы по байтам и предел работы за
  команду действуют также при фильтрации и подсчёте. Большой обход выполняется
  порциями в GUI или возвращает явную ошибку о превышении бюджета.
- `bbox` — `{min:[x,y,z],max:[x,y,z]}` в WCS либо `null`, если границы ещё
  недоступны. Чтение не должно запускать форматирование или redraw. Для типов без
  детальной геометрии вернуть общие поля и `geometry:null`. Обрабатывать
  `NO_DRAWING`, `OBJECT_NOT_FOUND`, `STALE_DRAWING` и `INVALID_ARGS`; на `/ipc`
  коды передаются в тексте `error`, в v1 — в структурированной ошибке.
- Сохранять JSON-строку в `result` действующего `/ipc`. Специализированный
  `zcad_query_*` может декодировать её и отдать структурированные данные MCP с
  `readOnlyHint:true`. Фильтрация, выбор разрешённых свойств и чтение остаются
  в Pascal. Для устройства или кабеля читать значения через
  `TVariablesExtender.entityunit.FindVariable` и `GetValueAsString`. Согласовать
  список доступных полей и проверить имена и представление значений на DXF.

Пример POST на `/ipc` для первой страницы `LINE` и ответ для одного объекта:

```json
{"id":"query-1","cmd":"QUERY_OBJECTS","args":[{"type":"LINE","limit":1}]}
```

```json
{"id":"query-1","status":"ok","result":"{\"drawingId\":\"d1\",\"revision\":\"r1\",\"objects\":[{\"objectId\":\"o1\",\"handle\":\"1F2\",\"type\":\"LINE\",\"layer\":\"0\",\"bbox\":{\"min\":[0,0,0],\"max\":[100,100,0]},\"selected\":false}],\"nextOffset\":1}"}
```

Приёмка включает открытый, пустой и закрытый чертёж, переключение файла или
пространства, выделение, объекты из DXF и свежие `LINE`/`CIRCLE`, поиск по обеим
формам ссылки и отсутствие extender. Проверить страницы без пропусков и дублей,
отклонение продолжения после правки, отсутствие изменений чертежа и Undo при
чтении, время отклика GUI на конечном большом чертеже и работу через MCP SDK.

## 4. Асинхронный API (предложение для согласования)

Сохранить старый `/ipc` для совместимости. Разделить постановку команды,
исполнение и чтение результата. За основу взять [анализ интерфейса][analysis]
и [проект API][spec] из ZCAD_MCP_SERVER.

| Маршрут | Назначение |
| --- | --- |
| `GET /api/v1/health` | Доступность HTTP, готовность GUI, глубина и ёмкость очереди |
| `GET /api/v1/commands` | Имена, схема входа, права и признак read-only для реально доступных команд |
| `POST /api/v1/commands` | `{id,command,args,timeoutMs?}` → `202` с `{id,jobId,state,statusUrl}` |
| `GET /api/v1/jobs/{jobId}` | `queued`, `running`, `succeeded`, `failed`, `cancelled` или `expired`. Малый `result` — JSON-значение, большой — `resultRef`. |
| `DELETE /api/v1/jobs/{jobId}` | Удаление задачи из очереди с подтверждением `cancelled`. Уже исполняемая задача без безопасной отмены даёт `409`. |
| `GET /api/v1/jobs/{jobId}/result?cursor=…&limit=…` | `{items,nextCursor,total?}` для неизменяемого снимка, ограниченного по байтам и элементам |

- HTTP worker валидирует JSON, лимиты и права и читает состояние задания. GUI
  исполняет CAD-обработчик и публикует результат как DTO без указателей на живой
  чертёж. Снимок принадлежит клиенту и заданию, имеет срок жизни и вытесняется по
  заданным лимитам. Начальные параметры для согласования — 1 МиБ на тело, 100
  заданий в очереди, 30 с до старта и 10 мин на хранение завершённого задания.
  Отдельно утвердить пределы workers, времени GUI, снимка и общего хранилища.
- Deadline до старта переводит задание в `expired` без выполнения. Для уже
  начатой операции без безопасного прерывания сохранить её фактический исход.
  Разрыв соединения оставляет задание доступным по ID. Повтор того же запроса
  с тем же `id` и клиентом в пределах TTL возвращает исходный job, другие
  аргументы с тем же `id` дают `409`.
- Проверять права до enqueue и при чтении задания или страницы. Разделить
  read и write, сохранить loopback по умолчанию. Использовать структурированные
  ошибки `{id?,error:{code,message}}` с `400` для схемы, `401/403` для доступа,
  `404` для неизвестного задания, `409` для конфликта, `413` для размера,
  `429` для заполненной очереди и `503` при неготовом GUI или остановке.
  Ошибка уже принятой команды отражается в `failed`.

Точки реализации — `uzvhttpserver.pas` (маршруты, доступ, lifecycle),
`uzvhttpipc.pas` (очередь, состояние, владение), реестр команд (схемы), GUI idle
(ограниченное исполнение), отдельный клиент v1 в MCP. Доступность v1 проверять
через discovery. Старые клиенты продолжают работать через `/ipc`.

Приёмка через SDK и живой ZCAD включает параллельные `id`, повтор мутации без
второго объекта, чужой `jobId`/cursor, переполнение, старт до и после deadline,
отмену queued/running, отключение клиента, TTL, чтение страниц одного снимка во
время правки чертежа и остановку под ограниченной нагрузкой с последующим запуском.
Повторить регрессии `/ipc`, widgets, Grist и отдельного TCP IPC. Конкретные
пределы, схему аутентификации и необходимость выгрузки файлов согласовать до v1.
