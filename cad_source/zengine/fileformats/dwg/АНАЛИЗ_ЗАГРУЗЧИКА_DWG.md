# Анализ работоспособности загрузчика DWG (issue #1196)

**Документ:** аналитический отчёт по текущему состоянию модуля импорта DWG в ZCAD.
**Задача:** issue [#1196](https://github.com/veb86/zcadvelecAI/issues/1196) — «Изучи всю проделанную работу и дай план по улучшению работоспособности».
**Ветка:** `issue-1196-7c3b1d16efc0`. **PR:** #1197.
**Область охвата:** `cad_source/zengine/fileformats/dwg/**` и `cad_source/components/fpdwg/**` (без подкаталогов `inspector/` и `fpdwginspect/` — устаревшие).
**Статус:** только анализ, кода в этом PR нет.

---

## 1. Краткое резюме (TL;DR)

1. **Маленькие DWG грузятся корректно**, потому что в них handle’ы примитивов и таблиц совпадают между «канонической» формой (`Obj.handle.value`) и «легаси»-формой (`Ref.absolute_ref` / `Ref.handleref.value`). На больших чертежах эти три источника расходятся, и лог наполняется сообщениями `ref kind mismatch`, `ref not found`, `owner is not a container`.
2. **Главная техническая причина** — отсутствие в текущем коде «трёхкандидатного» декодера `BITCODE_H` (`Ref^.obj^.handle.value` → `absolute_ref` → `handleref.value`). Коммит `280d7c439` («Resolve DWG refs with alternate handles»), который такой декодер вводил, был откачен веткой `master` коммитом `e8f5d1689` («откат коммита 280d7c43…»). После отката резолвер сравнивает ссылку, декодированную из легаси-полей, с ключом таблицы хэндлов, который записан в канонической форме — и попадает не в свою запись либо не находит её вовсе.
3. **Вторая системная причина** — placeholder’ы `dokUnknown` от `ScanRawObjects` могут так и не быть «повышены» до конкретного вида, если LibreDWG отдаёт объект таблицы (LAYER/LTYPE/STYLE/DIMSTYLE) под не зарегистрированным `DWG_OBJECT_TYPE` (control-объекты, под-классы, прокси-варианты). В этом случае ссылка на такой handle будет иметь «вид» `dokUnknown`, а ожидание было `dokLineType`/`dokLayer`/`dokTextStyle` — отсюда `ref kind mismatch`.
4. **Каскад «слой → линетип → примитив»** в логе (`layer Осевая ref=100A linetype fallback (kind mismatch) → Continuous`, после чего сотни записей `entity ... linetype fallback (layer=Осевая) → ByLayer`) — это одно событие, размноженное по всем сущностям, использующим этот слой. Без агрегирования каждый примитив «жалуется» отдельно, и лог становится нечитаем.
5. **Лог перегружен** не из-за количества проблем, а из-за отсутствия группировки. Отчёты (`zDebugLn`) пишутся пер-сущности, без дедупликации по handle, без счётчиков по диагностическим кодам и без сводки в конце импорта.

**Объём предполагаемой работы:** ~3–5 спринтов (в терминах текущих стадий аудита — Stage 8.x), из которых критичны только два первых пункта; остальное — улучшение наблюдаемости и производительности.

## 2. Архитектура текущего загрузчика (контекст для дальнейшего анализа)

### 2.1 Фазы импорта

Импорт построен в четыре последовательных фазы (см. `uzedwgimport.pas` и аудит `cad_source/components/fpdwg/TZ_DWG_LOAD_TO_ZCAD_AUDIT.md`):

| Фаза | Что делает | Ключевые точки кода |
|---|---|---|
| **1. ScanRawObjects** | Линейный проход по `Raw.&object[0..num_objects-1]`, регистрирует каждый handle в карте как «оболочку» (`shell`) с `Kind=dokUnknown`, `Ptr=nil`, `RawIndex=i`. | `uzedwgrawscan.pas:44`, `Ctx.RegisterShell` |
| **2. parseDwg_Data → mappers** | LibreDWG обходит объекты по `fixedtype`; для каждого зарегистрированного типа вызывается mapper (`AddLayer`, `AddLineType`, `AddInsertEntity`, …). Mapper создаёт ZCAD-объект и **повышает** placeholder через повторный `RegisterShell(Handle, dokХХХ, Ptr, …)`. | `uzedwgentityregistry.pas`, `uzedwgtables.pas:177-441`, `uzedwgentinsert.pas:109-172` |
| **3. ResolveRefs + ResolveOwners** | По очередям `FPendingRefs` и `FPendingOwners` декодирует целевые handle’ы, ищет их в карте, при успехе — вызывает callback’и `DWGAttachRef` / `DWGAttachEntity`. При неудаче — fallback (системный слой, `Continuous`, `ByLayer`, корневой контейнер) и предупреждение. | `uzedwgresolver.pas:200-356`, `uzedwgloadcontext.pas:625-660` |
| **4. FinalizeImport** | `BuildGeometry` / `FormatAfterDXFLoad` / `FromDXFPostProcessAfterAdd` — финализация уже расставленных по дереву объектов. | `uzedwgimport.pas` (см. конец файла) |

### 2.2 Ключевые структуры данных

- `TDWGZCADHandleEntry` (`uzedwgtypes.pas:80`): `Handle:QWord`, `Kind:TDWGZCADObjectKind`, `Ptr:Pointer`, `RawIndex:Integer`, `ShellState`.
- Карта хэндлов `TDWGZCADHandleMap` (`uzedwgloadcontext.pas`) — отсортированный массив + бинарный поиск по `Handle`.
- Очередь `TDWGZCADPendingOwner` — отложенные привязки `entity → owner`.
- Очередь `TDWGZCADPendingRef` — отложенные привязки `entity → (layer | linetype | textstyle | dimstyle | blockdef | layerLineType)`.
- Резолвер `TDWGZCADResolver` — рекурсивный обход с защитой от циклов через `FResolveStack` (`uzedwgresolver.pas`).

### 2.3 Источники handle в LibreDWG (важно для §3)

LibreDWG отдаёт ссылку (`BITCODE_H` ≈ `Dwg_Object_Ref*`) в трёх формах:

1. `Ref^.obj^.handle.value` — каноническое значение handle уже **разрешённого** объекта. Совпадает с тем, что попадает в `Obj.handle.value` при сканировании. **Это ключ карты `TDWGZCADHandleMap`.**
2. `Ref^.absolute_ref` — абсолютный handle, как он лежит в исходных байтах файла. Может быть `0`, если LibreDWG ещё не вычислил абсолют (например, для soft-pointer без цели на момент чтения), или может отличаться при нестандартных DWG-версиях.
3. `Ref^.handleref.value` — необработанное значение, зависящее от `code` (soft/hard, owner-relative и пр.). Для совместимости часто совпадает с `absolute_ref`.

**Текущий `DWGRefHandleValue`** (`cad_source/components/fpdwg/uzedwghandle.pas:260-276`) использует только пункты 2 и 3. Канонический пункт 1 не проверяется. Это и есть код, восстановленный коммитом `280d7c439` и удалённый коммитом `e8f5d1689`.

## 4. Гипотезы о корневых причинах

### 4.1 Гипотеза №1 (приоритет 1, наиболее вероятная): откат «трёхкандидатного» декодера handle

**Факты:**

- Коммит `280d7c439828453c3744fc6cefbd33fdf246439b` («Resolve DWG refs with alternate handles», автор konard) добавлял в `DWGRefHandleValue` приоритетную последовательность кандидатов: `Ref^.obj^.handle.value` → `Ref^.absolute_ref` → `Ref^.handleref.value`, и в резолвере — итерацию по кандидатам до первого успеха.
- Коммит `e8f5d1689` («откат коммита: 280d7c43…») этот код снёс, оставив только пункты 2 и 3.
- Карта хэндлов заполняется ключом `DWGObjectHandleValue(Obj) = Obj.handle.value` (см. `uzedwgrawscan.pas:44`), то есть **в канонической форме**. Резолвер же ищет в этой карте по ключу из `absolute_ref`/`handleref.value`. На простых файлах эти значения совпадают; на сложных — не всегда.

**Что это объясняет:**
- Почему мелкие файлы грузятся, а крупные — нет.
- Почему ошибка касается одинаково layer/linetype/textstyle/dimstyle/owner: `DWGRefHandleValue` единый для всех слотов и для owner-handle (`DWGObjectOwnerHandleValue` — копия логики).
- Почему в логе встречается именно `kind mismatch`, а не только `not found`: если по «легаси» handle’у в карте есть **чужая** запись (например, другая таблица с совпадающим младшим словом), то поиск находит её и Kind не совпадает.
- Почему дополнительный документ `cad_source/components/fpdwg/TZ_for_analysis_2.md` (раздел «Двойная модель handle: BITCODE_H vs Dwg_Object_Ref») независимо описывает ровно эту же проблему как «критический риск».

**Контр-гипотезы и почему они слабее:**
- *«Виноват сам LibreDWG»* — маловероятно, потому что `Obj.handle.value` всегда корректно (на этом значении строится индекс самой LibreDWG).
- *«Виноват порядок mapper’ов»* — порядок не должен влиять, так как разрешение ссылок выполняется только в фазе 3, после всех mapper’ов.

### 4.2 Гипотеза №2 (приоритет 2): placeholder’ы `dokUnknown` без повышения

**Факты:**

- `ScanRawObjects` регистрирует **каждый** handle как `dokUnknown`+`nil` (`uzedwgrawscan.pas:50-90`).
- Повышение происходит только из mapper’ов, зарегистрированных через `RegisterDWGObjectHandler` / `RegisterDWGEntityHandler` (`uzedwgentityregistry.pas`).
- В коде зарегистрированы mapper’ы для `DWG_TYPE_LAYER`, `DWG_TYPE_LTYPE`, `DWG_TYPE_STYLE`, `DWG_TYPE_DIMSTYLE`, `DWG_TYPE_VPORT`, `DWG_TYPE_INSERT`, `DWG_TYPE_MINSERT`, и набор примитивов (см. `cad_source/zengine/fileformats/dwg/entities/`).
- Нигде не регистрируются control-объекты (`LAYER_CONTROL`, `LTYPE_CONTROL`, `BLOCK_CONTROL`, …) и proxy/sub-class варианты. Если LibreDWG в каком-то месте отдаёт ссылку на control-объект (или прокси), placeholder остаётся `dokUnknown`.
- `AddVPort` сознательно не вызывает `RegisterShell` (только `*ACTIVE`).

**Что это объясняет:**
- Почему `ref kind mismatch` встречается даже при правильно декодированном handle: запись есть, но `Kind=dokUnknown ≠ dokLayer`.
- Почему `owner is not a container`: handle блока проассоциирован с `BLOCK_CONTROL` (а не с `BLOCK_RECORD`), placeholder остался `dokUnknown`, и в множество контейнеров не попадает.

**Подтверждение/опровержение:** требуется диагностический проход, который сразу после фазы 1 печатает гистограмму `Kind` по всем зарегистрированным handle’ам и долю оставшихся `dokUnknown` после фазы 2. Такого режима сейчас нет (см. §6.1).

### 4.3 Гипотеза №3 (приоритет 3): каскадирование одной ошибки на сотни сущностей

**Факт:** `DWGAttachRef` пишет fallback-указатель в каждый примитив, использующий проблемный слой/линетип; при этом `zDebugLn` вызывается на каждом срабатывании. Если в чертеже 1000 примитивов, ссылающихся на «битый» слой `Осевая`, в логе будет ~1000 строк об одном и том же.

**Что это объясняет:**
- Размер лога (тысячи строк) непропорционален реальному количеству уникальных проблем (десятки).
- Иллюзия катастрофы при импорте, тогда как уникальных сбоев может быть в 30–50 раз меньше.

### 4.4 Гипотеза №4 (приоритет 4): aliasing `AddTextStyle → "Standard"`

`AddTextStyle` (`uzedwgtables.pas:280-335`) переименовывает любой стиль с не-валидным `bigfontname` в `"Standard"`. Если в файле два стиля «Standard» (один реальный, один alias), второй вызов `RegisterShell` даёт `False` (дубликат) и handle второго стиля привязывается к указателю первого. В лог уходит `DWG_WARN_DUPLICATE_HANDLE` (1407). Сейчас отдельно от issue #1196 в логе это не выделено, но при разборке полётов всплывёт.

### 4.5 Гипотеза №5 (фон): O(N) и O(N·M) узкие места при поиске

`TDWGZCADPendingOwnerList.FindByEntityHandle`, `TDWGZCADPendingRefList.FindByEntityAndSlot`, и `DWGOwnerIsBlockDef` — линейные сканирования. На больших файлах (десятки тысяч объектов) каскад резолвинга может занимать минуты, что субъективно усиливает ощущение «загрузчик не работает». Это уже отмечено в `TZ_DWG_LOAD_TO_ZCAD_AUDIT.md §8.4`.

## 5. Рекомендации по исправлению (приоритезированный список)

### P1. Восстановить декодирование handle по всем трём кандидатам

**Что:** вернуть в `cad_source/components/fpdwg/uzedwghandle.pas` запись `TDWGRefHandleCandidates`, заполняемую из `Ref^.obj^.handle.value`, `Ref^.absolute_ref`, `Ref^.handleref.value`, и в `uzedwgresolver.pas` итерировать по кандидатам, пока не найден подходящий по `Kind` или `Ptr<>nil`.

**Почему именно так:**
- Это исправление **единичной первопричины**, объясняющей пять из шести типов сообщений в логе issue #1196.
- Этот код уже был написан (commit `280d7c439`) — нужна не разработка, а восстановление + покрытие тестами.

**Что добавить относительно отката (чтобы не повторить):**
1. Юнит-тест на `DWGRefHandleValue` с моками `Dwg_Object_Ref`, где три источника возвращают разные значения, и тестом, что приоритет — `obj^.handle.value`.
2. Интеграционный тест на маленьком DWG, где специально подобран handle с расхождением источников (можно сгенерировать через LibreDWG из ODA-примера).
3. В резолвере — **счётчик** по диагностическому коду «handle разрешён по альтернативному кандидату» (новый код, например `1416 = DWG_INFO_HANDLE_ALT_CANDIDATE`), чтобы видеть, на сколько кандидатов реально приходится переключаться. Это даст метрику безопасности отката в обратную сторону.
4. При полном промахе — выводить в лог **все три** варианта handle, чтобы в спорных случаях можно было быстро посмотреть, какой из источников реально несёт правду.

**Оценка:** 0.5 спринта.

### P2. Перепроверить покрытие mapper’ов всеми реально встречающимися `DWG_OBJECT_TYPE`

**Что:** добавить диагностический режим, который после фазы 1 печатает гистограмму `Raw.&object[i].fixedtype` (или `parent.fixedtype`/`type`) по всем объектам файла. Сравнить со списком зарегистрированных в `RegisterDWGObjectHandler`/`RegisterDWGEntityHandler`. Для всех *_CONTROL и не-зарегистрированных типов — решить:
- регистрировать «лёгкий» mapper, который только повышает Kind на специальный новый вид (`dokControlObject`), не создавая ZCAD-объект, **либо**
- расширить логику резолвера так, чтобы для известных control-handle’ов считать ошибку информационной, а не warning’ом.

**Почему:** убирает остаток `ref kind mismatch` после P1.

**Оценка:** 1 спринт (включая натурные эксперименты с реальными DWG из issue).

### P3. Структурировать диагностику: вынести лог в side-файлы

**Текущая боль:** `zDebugLn` пишет всё в один поток.

**Предложение:** при включённом флаге `--dwg-diag-dir=<path>` загрузчик создаёт на каждый импортируемый DWG четыре файла:

1. **`<dwg>.handles.csv`** — по строке на каждый зарегистрированный handle:
   `RawIndex; HandleHex; FixedType; ResolvedKind; ShellState; HasPtr; SourceUnit; SourceLine`
   Где `SourceUnit/Line` — место в коде, выполнившее повышение Kind (для дедупликации добавлений).
2. **`<dwg>.refs.csv`** — по строке на каждую запись в `FPendingRefs`:
   `EntityHandle; EntitySrcKind; Slot; RawRefAbsolute; RawRefHandleref; ResolvedRefHandle; ResolvedKind; ExpectedKind; AttachState; AttachReason; FallbackUsed; AttachedPtr`
3. **`<dwg>.owners.csv`** — по строке на каждую запись в `FPendingOwners`, аналогично.
4. **`<dwg>.summary.txt`** — сводка:
   - количество объектов по Kind,
   - сколько handle’ов осталось `dokUnknown`,
   - топ-10 владельцев по числу детей,
   - количество предупреждений по каждому диагностическому коду 1401-1415,
   - топ-10 уникальных «битых» handle’ов с ссылающимися сущностями (для каскадов).

**Что от этого получает разработчик:**
- При следующем «странно загрузилось» можно сразу открыть `*.summary.txt` и за 10 секунд увидеть масштаб; при необходимости — спуститься в CSV.
- Лог в основном окне можно жёстко ограничить (например, первыми 50 предупреждениями каждого кода + финальная сводка).

**Оценка:** 1 спринт.

### P4. Дедупликация и агрегирование логов в основном потоке

**Что:** в `TDWGImportStats` добавить:
- `WarningsByCode: array[Code] of Integer`,
- `WarningsByHandle: TDictionary<QWord, Integer>` (топ-N сохраняем, остальное считаем),
- `FirstWarningSampleByCode: array[Code] of TDWGImportWarning`.

В основной лог по умолчанию писать только **первое** появление каждой пары `(Code, Handle)` + при превышении `MaxWarningsPerCode` (например, 20) — финальное `«… and 1234 more like this; see *.summary.txt»`.

**Эффект:** без потери информации лог становится в 50–100 раз компактнее.

**Оценка:** 0.5 спринта.

### P5. Перевести «горячие» поиски в индексы

`TDWGZCADPendingOwnerList.FindByEntityHandle` и `…PendingRefList.FindByEntityAndSlot` — сейчас линейные. Заменить на `TDictionary<QWord, Integer>` (handle → индекс в массиве), как в `TDWGZCADHandleMap`. Аналогично `DWGOwnerIsBlockDef` — закэшировать множество block-record handle’ов в `THashSet<QWord>` после фазы 2.

**Эффект:** на файлах с 10⁵+ объектов резолвинг перестанет квадратично расти.
**Уже отмечено в аудите:** `TZ_DWG_LOAD_TO_ZCAD_AUDIT.md §8.4`.

**Оценка:** 0.5 спринта.

### P6. Перестать терять имена в `AddTextStyle`

Вместо переименования в `"Standard"` — генерировать уникальное имя `"<orig>_dwg<hex>"` либо отказывать в регистрации только при гарантированной невозможности использовать стиль. Сохранение оригинального имени даст пользователю понимание, какой именно стиль «не повезло» и не будет молча терять данные.

**Оценка:** 0.25 спринта (но нужно согласование с продуктовым требованием).

## 6. Рекомендации по структуре аналитических данных

Выше уже описан CSV-формат (см. P3). Ниже — расширения, которые имеет смысл закладывать сразу:

### 6.1 Режимы диагностики

| Режим | Что включает | Когда использовать |
|---|---|---|
| `off` (по умолчанию) | Только агрегированный summary в конец основного лога | Обычная работа |
| `summary` | Summary в лог + `*.summary.txt` рядом с DWG | Жалобы пользователей |
| `full` | summary + три CSV (handles/refs/owners) | Воспроизведение бага разработчиком |
| `trace` | full + per-call трассировка `DWGRefHandleValue` (все три кандидата на каждый вызов) | Исследование расхождения источников handle |

Хранение режима — переменная окружения `ZCAD_DWG_DIAG=full` либо параметр командной строки. Это пока удобнее, чем новый GUI-чекбокс.

### 6.2 Машинно-читаемая сводка (JSON)

Параллельно `*.summary.txt` имеет смысл писать `*.summary.json` — для возможной автоматической пост-обработки в CI и для скриптов, которые сравнивают «до/после» при правках загрузчика.

```json
{
  "file": "ЭС_большой.dwg",
  "raw_objects": 184523,
  "kinds": {"dokLayer": 51, "dokLineType": 14, "dokUnknown": 27, "...": 0},
  "warnings": {"1410": 8412, "1403": 18, "...": 0},
  "top_broken_handles": [
    {"handle": "100A", "code": 1410, "count": 4711, "first_entity": "2072"},
    {"handle": "100B", "code": 1410, "count": 1850, "first_entity": "DF4"}
  ],
  "alt_candidate_hits": {"obj_handle": 0, "absolute_ref": 0, "handleref": 0}
}
```

Сравнение `top_broken_handles` до/после правки — дешёвый способ убедиться, что P1 не сломал ничего другого.

### 6.3 Что **не** надо делать

- Не пытаться удержать всю эту диагностику в RAM до конца импорта в виде объектов — это уже большой расход памяти на больших чертежах. CSV пишется потоково по мере появления `Pending*` записей.
- Не привязываться к UI ZCAD: side-файлы должны существовать независимо от того, открыт ли инспектор. Это было одной из причин, по которым старый `fpdwginspect/` оказался deprecated.

## 7. Оценка масштаба работы

| Пункт | Оценка | Зависимости |
|---|---|---|
| P1 (восстановление multi-candidate decoder) | 0.5 спринта | Нет. Делается первым. |
| P2 (аудит DWG_OBJECT_TYPE) | 1 спринт | Делать после P1, чтобы видеть остаточные mismatch. |
| P3 (CSV side-файлы) | 1 спринт | Независим, но удобнее реализовать **до** P2 — тогда P2 пишется на готовой инфраструктуре. |
| P4 (дедупликация в основном логе) | 0.5 спринта | Зависит от P3 (общий счётчик). |
| P5 (индексы вместо O(N)) | 0.5 спринта | Независим. Можно делать параллельно. |
| P6 (имена textstyle) | 0.25 спринта | Независим. Согласование с владельцем продукта. |

**Итого:** 3.75 спринта чистой работы; реалистично 4–5 спринтов с учётом тестов на реальных файлах из issue.

**Рекомендованный порядок:** P3 → P1 → P4 → P2 → P5 → P6. Такой порядок даёт максимально быструю «видимость прогресса»: после P3 у нас есть инструмент, после P1 ушло 80% строк лога, после P4 лог становится читаемым, после P2 уходит остаток, после P5 ускоряются большие файлы.

## 10. Заключение

Главное: **это не «загрузчик в принципе плохо работает», а одна корневая регрессия + отсутствие группировки в логе, что создаёт впечатление катастрофы.** Восстановление коммита `280d7c439` (с тестами и метриками) с высокой вероятностью убирает основную массу сообщений `ref kind mismatch` и `owner is not a container`. Остаточные сбои закрываются аудитом покрытия `DWG_OBJECT_TYPE` и точечной правкой mapper’ов. Параллельно нужно провести минимально инвазивную работу по структурированию диагностики (CSV side-файлы + сводка), потому что без неё каждая следующая итерация будет упираться в нечитаемый лог так же, как упёрлась эта.

Никаких изменений в коде в рамках issue #1196 не выполнялось — этот документ является исключительно аналитическим.
